## 1. 阻断级缺陷：v1.8-b 视觉事实行错位一轮

### 1.1 现象（实测，非推断）

用 mock server 抓真实请求体，三轮对话实测：

| 轮次 | 带图 | 带事实行 | 说明 |
|---|---|---|---|
| 第 1 轮 | ❌ | ❌ | 基线 |
| 第 2 轮 | ✅ | ❌ | **有图，但模型收不到「你看到了一块 800×600 的屏幕区域」** |
| 第 3 轮 | ❌ | ✅ | **无图，却收到上一轮那张图的事实行** |

边界场景实测：

| 场景 | 实测结果 |
|---|---|
| 连续三轮带图 | 第 1 轮无事实行；第 2 轮的事实行是**第 1 轮的尺寸**（100×50），而图是第 2 轮的（200×100）→ **尺寸错配** |
| 最后一轮带图后不再开口 | 事实行**永远不送达**，会话结束时 `pendingVisionNote` 残留 `"【你看到了一块 640×480 的屏幕区域】"` |

**证据**：`.workbuddy/audit-20261027/probe-vision-order.js` / `probe-vision-order2.js`（可复跑，不改源文件）。

### 1.2 根因（源码事实）

`src/brain.js` 的 `ask()` 执行顺序：

```
① let messages = this.memory.build(dynamicContext);   // brain.js:1451
      └─ 内部 _visionNote() → takeVisionNote() 把 pendingVisionNote 取走并清空
② const visionPick = this.takeVisionPick();           // brain.js:1462
③ this.pendingVisionNote = formatVisionNote(...)      // brain.js:1471  ← 赋值在 build 之后
```

**赋值晚于取值，永远差一轮。**

### 1.3 影响面（诚实标注边界）

- **不是「看不见图」**：图本身挂载正确（`attachImageToLastUser` 工作正常），模型确实收到了图。
- **是「少了一句客观说明」+「多了一句过期的说明」**：模型看图时不知道自己看的是多大一块；下一轮无图时反而被告知"你看到了一块 800×600 的区域"。
- **与设计意图冲突**：`v1.8-b` 的设计写「程序只陈述看到了多大一块区域，描述内容是模型的事」。事实行缺席时，模型没有尺寸锚点；错位时，它会把旧尺寸当成本轮事实——**这正是「数据不伪造」铁律要防的形态**。
- **严重度定为 🔴 阻断**：不是因为影响大，而是因为它**违反项目自己的不变式**，且当前无任何断言覆盖。

### 1.4 为什么 93 项断言没抓到（这是更值得记的一条）

`test/v18-vision.test.js` 对视觉的验证全部是**源码字符串断言 + 纯函数单测**：

| 断言类型 | 例子 | 为什么抓不到 |
|---|---|---|
| 纯函数单测 | `formatVisionNote(800,600)` 返回含 800/600 | 测的是函数，不是「它有没有被调用、在什么时机被调用」 |
| 源码字符串 | `brainSrc.includes('setVisionProvider(() => this.takeVisionNote())')` | 只证明**接线存在**，不证明**时序正确** |
| 源码字符串 | `/\[bedsideNote, selfNote, reunionNote, visionNote, suffix\]/` | 只证明 tail 数组里有这个位置 |

全仓 grep `你看到了一块`：**除 `formatVisionNote` 自身单测外，零处**——没有任何一条断言验证「事实行真的进入了本轮 messages」。

**这是「测了接线，没测行为」的典型**。与 `d13` 那次「history 快照取在 build 之后 ⇒ 恒真断言」同型，只是这次连恒真都算不上，是**根本没测**。

### 1.5 修复方案（已验证机制成立）

`probe-fixcheck.js` 实测：把赋值挪到 `memory.build()` **之前**，事实行正确进入本轮 messages，且 `pendingVisionNote` 被正确消费为空。

```js
// 现在（brain.js:1451-1471）
let messages = this.memory.build(dynamicContext);
const visionPick = this.takeVisionPick();
if (visionPick && ...) { ...; this.pendingVisionNote = formatVisionNote(...); }

// 应改为：先决定本轮有没有图、先把事实行写好，再 build
const visionPick = this.takeVisionPick();
if (visionPick && visionPick.dataUrl) {
  if (!modelSupportsVision) { this.lastVisionError = 'MODEL_HAS_NO_VISION'; this.pendingVisionNote = ''; }
  else { this.pendingVisionNote = formatVisionNote(visionPick.width, visionPick.height); }
}
let messages = this.memory.build(dynamicContext);   // ← 此时能取到事实行
if (visionPick && ...) { messages = attachImageToLastUser(messages, visionPick.dataUrl); }
```

⚠️ **两点必须同时处理，否则修一半**：
1. `attachImageToLastUser` 仍须在 build 之后（它改的是 messages 副本）；
2. 若 `build()` 抛错或后续请求失败，`pendingVisionNote` 已被消费——需要决定语义（建议：与 reunion 同款，失败即丢，不补发）。

### 1.6 必须补的断言（否则修完仍无防线）

现有 93 项一条都不用删，但**必须新增行为级断言**（建议 `v18-vision.test.js` 93 → 约 99 项）：

| 新断言 | 判据 |
|---|---|
| 带图那一轮，最后一条 user 的 content 数组含事实行 | 真的 build 一次并检查 |
| 事实行里的尺寸 == 本轮 `stageVisionPick` 的尺寸 | 防错配 |
| 下一轮（无图）**不得**出现事实行 | 防残留 |
| 连续两轮带图，第 2 轮事实行尺寸是第 2 轮的 | 防落后一轮 |
| 最后一轮带图后 `pendingVisionNote` 为空（除非刻意保留） | 防静默堆积 |

## 7. 版本号建议（按你的要求，只作建议不替你定）

**建议：合并为 `v1.8.0`**，理由同你所述（v1.7 从未单独发布 / v2.0 已移出编号 / 语义连贯）。

**但补一条你可能没考虑的风险**：

`VERSION-RESCHEDULE.md` 已把「v1.9 / v2.0」移出编号，改成条件触发制。那么 `1.8.0` 之后的下一个版本号**是什么**？

**建议在 `VERSION-RESCHEDULE.md` 补一句**：「v1.9 / v2.0 两个号**永久作废不复用**，后续版本从 `1.8.x` 起按语义化版本递增」。否则将来有人会问「1.9 去哪了」。

## 8. 我的判断（供你参考，不是结论）

这次审核最值得记的不是那个 bug 本身，而是：

**「93 项断言 + 275 项门禁全绿」和「功能实际不按设计工作」可以同时成立。**

这与你记忆里那条「测试通过只证明这次运行没报错，不证明代码对」是同一件事的两个面：那次说的是「测的不是你的代码」，这次说的是「测的是零件不是装配」。

**建议把这条写进 `life-dev-guide`**：新增功能除了单测与源码断言，**必须有一条端到端行为断言**（真的构造对象、真的跑一轮、检查真实产出）。否则「接线存在」会被当成「功能可用」。
