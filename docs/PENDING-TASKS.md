> 🔴 **这条措辞有判别力，原因必须说清**（否则看起来像「她随口提了个时长」）：

### 6.5 更正：`visionTokens` 恒为 null 的根因（2026-10-27 实测）

原文 §6.3 写「实测一次看图约 550 token」，读起来像 provider 报的数。**它不是。**

| 事实 | 实测依据 |
|---|---|
| provider 返回的 `usage` 里**没有** image token 字段 | `src/deepseek.js:179` / `:270` 只透传 `j.usage`；`src/usage-normalizer.js` 只映射 prompt / completion / cache_hit / cache_miss 四个字段，全仓 grep `image_tokens` / `imageTokens` **零命中** |
| `vision-audit.jsonl` 的 `visionTokens` **永远是 null** | 全仓只有 `main.js` 的 `appendVisionAudit` **读**这个字段，**没有任何地方写** |
| 那个「550」是怎么来的 | 是按 `prompt_tokens` 总量与该轮纯文本基线**推算**的，不是 provider 归因给图片的 token 数 |

**结论**：要真实填上 `visionTokens`，只有两条路，且都不该现在做 ——
① 同轮带图 / 不带图各发一次对比差值（多花钱，且两次请求内容不可能完全一致）；
② 不填 token 数、改记本轮 `prompt_tokens` 总量（能反映真实成本，但无法归因给「图」）。
用户 2026-10-27 决定：**不改行为逻辑**，只把文档改成如实描述。

### 8.2 `refused` 投影：查清了但**设计上还不能做**（2026-11-05）

> 来源：`docs/agent/audit-agent-framework-2026-11-05.md` 问题 #10（P2）。
> 审计方给的建议是「要么在动作史里投影，要么明确它不是给她看的」。
> 施工单 B-3 的决定是**这一轮不做，只记录**。下面是查清的全部事实，避免下次从头再查一遍。

**① 事实：`refused_by_subject` 记录里没有 `proposalId`**

`main.js:216-235` 的 `auditProposalRefused` 写出的记录，实测 keys 是：

```
at, channel, outcome, capability, via, hint, reason
有 proposalId: false
```

**② 事实：而 `projectProposalChains` 按 `proposalId` 聚合，没有 id 的在第一步就被丢**

`src/agent-history.js:57-58`：

```js
const id = typeof rec.proposalId === 'string' ? rec.proposalId : '';
if (!id) continue;
```

⇒ **refused 现在根本进不了动作史。不是「投影写错了」，是「数据没有能被聚合的键」。**

**③ 为什么不能简单补一个合成 id + `proposalSource: 'selfNote'`**

最省事的补法是给拒绝记录一个合成 id，并标成 `selfNote` 让判据①（只收她自发的）放行。

**但那是错的**：`proposalSource: 'selfNote'` 是给**已写成的便签**用的来源标签。
把它贴到「没写成」的记录上，会让 `SELF_SOURCES` 那道过滤**失去区分力** ——
以后分不清「她写成了」和「她拒绝了」。

**④ 正确做法（下一轮再谈）**

给 refused 一个**独立来源值**（如 `'selfRefusal'`），它才是一等公民：

| 要改的地方 | 改什么 |
|---|---|
| `src/agent-history.js:36` | `SELF_SOURCES` 加上 `'selfRefusal'` |
| `src/agent-interfaces.js` | `PROPOSAL_SOURCES` 白名单同步 |
| `src/agent-history.js:217` | 渲染分支**已经有了**（`kind === 'refused'`），不用改 |

**这是一次小协议变更，值得单独一轮，别塞进 B 批。**

**⑤ 还有一个更根本的理由：样本不够且样本是错的**

真实数据里 `refused_by_subject` 只有 **1 条**，`reason: EXPLICIT_REFUSAL`，
`hint` 是「今天聊的整理成一份方案.md」。

**而那条是能力误判**——她说「存到沙盒我碰不到，我这扇窗里没有那个抽屉」，
实际 `workspace.write` 在 D-5 就打开了，她当天 13:50 就写成了第一张便签。

⇒ **拿它当负样本，会强化「她倾向于拒绝」这个错误倾向。**
（审核方的补充：即使是**正确**的拒绝，拿它当统计样本也会产生行为偏移。
  所以正确做法是**只投影事实、不做统计**。）

**⑥ 什么时候再做**

等 `refused` 自然积累到 10 条以上、且能区分「能力误判」与「主体性拒绝」之后再谈。
在那之前，`agent-history.js:144` 的 `kind = 'refused'` 分支与 `:217` 的渲染分支
**保持存在但不被触达**——它们是对的，只是没有数据。

**不建议现在做**：v1.9 看板、v2.0 检索 —— 数据量只有目标的 12% 和 0.2%（2026-10-27 复测：窗口 6/50、经历 10/5000）。

### 8.3 `S-3` 派生待办：沙盒不可用时给她的运行时告知通道（2026-11-12）

> 来源：`S-3` 沙盒初始化失败降级改造（`main.js` `agentSandboxUnavailable`）。

- **现状**：当桌面路径不可用或 `LifeSandbox` 撞上同名文件导致沙盒降级为 `null` 时，`app.whenReady` 已不再中断启动，写能力也自动关闭；但 `src/persona.js:32` 与三条 `SYS`（`WANT_TO_LEAVE_SYS` / `OBSERVER_JOURNAL_SYS` / `PROPOSAL_DRAFT_SYS`）仍静态写着「你可以在那里留下文字，程序会替你把字写进去」。
- **缺口**：与 2026-11-01「规则落后于能力」属同一类镜像问题——当时是她以为碰不到沙盒实际碰得到，现在降级态下则是她以为写得了实际写不了。
- **后续**：需要一条运行时状态告知通道（如根据 `agentSandboxUnavailable` 在当轮尾部或系统约束注记一行「沙盒暂时不可用」），让能力认知与降级事实一致。**待后续单独立项，不在 `S-3` 修复内顺手改 persona。**
- **实现约束**：落实该通道时需将 `agentSandboxUnavailable` 从 `app.whenReady` 块级作用域提升至 `agentBuildDeps` 或模块顶层（参考 `proactiveAuditLog` 的 TDZ 教训）。
