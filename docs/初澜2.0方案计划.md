## 一、核实过的事实（本机实测，可复现）

### 1.1 沙盒子目录**在权限上允许，在执行器上失败**

前序总监版方案的核心是 `LifeSandbox/plans/` 与 `LifeSandbox/tickets/` 两个子目录，原文说「无需突破现有的沙盒目录和扩展名白名单」。

**前半句对，后半句不完整。** 三层事实：

| 层 | 结论 | 证据 |
| :--- | :--- | :--- |
| 权限层 | ✅ **子目录本就允许** | `agent-interfaces.js` 的 `_scopeAllowed` 用前缀匹配（`target === root \|\| target.startsWith(root + sep)`） |
| 执行层 | ❌ **不建目标父目录** | `agent-transaction.js` 只对**自己的** `dir` / `backupDir` 做 `mkdirSync(recursive)`，不管写入 target |
| 命名层 | ❌ **生成不出子目录路径** | D-27 的 `buildSandboxScope()` 明确拒绝任何含分隔符的名字（`if (/[\\\\/]/.test(h)) return null;`） |

**结论**：子目录方案不是不可行（加几行建目录即可），但「零前置依赖」这个说法不成立。而平铺的 `.md` 走现有 `workspace.write` 原本就能直接落盘。

### 1.2 新增一个能力，要改 6 处（其中 4 处是安全边界文件）

| 文件 | 位置 | 性质 |
| :--- | :--- | :--- |
| `src/agent-interfaces.js` | `:40` `CAPABILITIES`（`Object.freeze`） | 🔴 安全边界 |
| `src/agent-interfaces.js` | `:84` `CAPABILITY_META` | 🔴 安全边界 |
| `src/agent-executor.js` | `:54` `EXECUTABLE_CAPABILITIES`（`Object.freeze`） | 🔴 安全边界 |
| `src/agent-executor.js` | `:431` 执行分支 | 🔴 安全边界 |
| `ui-agent-confirm.js` | `:46` / `:119` / `:120` 能力名→中文标签 | 展示层 |
| `src/agent-ipc.js` | **12 处** `workspace.write` 字面量判定 | 🔴 安全边界 |

> ⚠️ **本机复核修正**：v1.1 原文写「9 处」，实测为 **12 处**（`:215 :226 :291 :334 :378 :468 :473 :484 :495 :506 :743` 等）。
> 数字不影响结论方向，但**方向变得更谨慎**——多 3 处意味着多 3 个可能漏改的判定点。

**结论**：每加一个能力都要重新论证五道闸门没松。在 D-27 刚落地、还没实机充分跑出数据的时候，**绝对不碰这 4 个安全边界文件**。

### 1.3 审计日志存不下长预览，且不该当数据源

`src/agent-interfaces.js:589`：任何字符串字段超过 500 字就被截到 500。

```js
if (typeof v === 'string' && v.length > 500) safe[k] = v.slice(0, 500);
```

**更根本的问题**：`agent-audit.jsonl` 是安全审计（append-only、记录谁在什么时候请求了什么权限、被什么理由拒绝）。观察记录是**行为数据**。两者混在一个文件里，将来任何一方改格式都会波及另一方。

**结论**：观察记录另起文件 `agent-observations.jsonl`，不进 `agent-audit.jsonl`。

### 1.4 她**读得到**自己写过的东西

- `main.js` → `brain.askForSelfNote()` 拿内容
- → `proposeInternal(..., 'selfNote', content)` 盖戳
- → 执行器 `SELF_NOTE_EXEMPT` 免确认直写
- → 关窗时 `_engraveSelfNotes()` 铸进 `experiences.jsonl`
- → 下轮 `memory._drainSelfNotes()` 把**内容**注入尾部

**所以：只要执行成功，她就读得到。** 只有「不执行（如观察档）」或「执行失败」时才需要特殊处理回流。

### 1.5 真实审计里她**从未拒绝过立项**

实测 `%APPDATA%\Life\agent-audit.jsonl`，30 条：

```text
proactive-offer      | dispatched      21
agent:propose-action | accepted         3
agent:execute        | executed         2
agent:execute        | rejected         1
agent:execute        | failed           1
agent:confirm-action | recorded         1
chat-failed          | failed           1
```

`refused_by_subject` = **0**，`draft_unavailable` = **0**。

**影响**：`refused` 回声这个功能目前没有数据可回声。真要做，得从第一次拒案开始建账。

### 1.6 关于「0 次拒绝」这个前提有时效

D-27 已经把 `refused_by_subject` / `draft_unavailable` 写进审计了。只要 `agentTriggerEnabled` 打开（默认 `false`，`config.js:70`）、正常聊几次，这两个数就会从 0 变成非 0。

**所以「她拒过 0 次，所以不做回声」这个理由会自己失效。** 等跑出真实数据后，按第五节顺序复核并启动回声即可。

## 二、方案：`observe` 观察档

### 2.1 要解决的真问题

> **以后每加一个「她自发会做事」的能力，我怎么在放它出去之前，先看她在没人时会怎么做？**

这个问题现在没有答案。现在的二选一是：

- 免授权直接做（`selfNote` 现状）——出了事才知道
- 每次都问她——毁掉自发行为本身

`observe` 是第三档：**照常想、照常拟稿，但不落盘，只记录。**

### 2.2 三档与拦截水位线

| 档位 | 她自发想做事时 | 何时拦截 | 落盘 | 记录 |
| :--- | :--- | :--- | :--- | :--- |
| `off` | 不评估，直接跳过 | **调用 `brain.askFor*()` 之前**直接 `return`（零 LLM 开销） | 否 | 否 |
| `observe` | 照常想、照常拟稿 | **`brain.askFor*()` 拿到非空正文之后、`proposeInternal` 之前**拦截 | **否** | 写一条观察记录（含完整正文） |
| `auto` | 照常想、照常拟稿 | 不拦截，走现有 `proposeInternal` → `executeInternal` | **是**（现状） | 现状（审计 `executed`） |

> **边界约束（防空记录污染）**：`observe` 档下，如果她在 `brain.askFor*()` 阶段自己决定「这次不想写」（未产出正文，`refused_by_subject` 或 `draft_unavailable`），**不写 `agent-observations.jsonl`**（仍按 D-27 原有逻辑处理）。
> 确保 `agent-observations.jsonl` 里的每一行都是实打实的完整成稿。

**默认值：已有自发能力 `auto`，未登记的新能力 `observe`。**

```js
// src/config.js
const DEFAULT_AGENT_CAPABILITY_MODES = {
  selfNote: 'auto',
  observerJournal: 'auto',
};

function getCapabilityMode(config, capabilityKey) {
  const modes = (config && config.agentCapabilityModes) || {};
  const v = modes[capabilityKey];
  if (v === 'off' || v === 'observe' || v === 'auto') return v;
  return DEFAULT_AGENT_CAPABILITY_MODES[capabilityKey] || 'observe';
}
```

> **为什么不把 `observe` 设为全局默认**：`selfNote` / `observerJournal` 的免授权是 D-17 用户拍板过的（`agent-executor.js:444` 注释原文「D-17（用户拍板 C1）」）。
> 把它们降成 `observe` 是**收权**，不是给权。

### 2.3 观察记录：另起文件，存完整正文 + 定长轮转

**文件**：`agent-observations.jsonl`，落在 `app.getPath('userData')`，与 `agent-audit.jsonl` 同目录但不混写。

**一条记录**：

```json
{
  "at": 1793600000000,
  "capability": "selfNote",
  "intentKind": "wantToLeaveSomething",
  "proposalSource": "selfNote",
  "scopeName": "note-2026-11-01-abcd.txt",
  "content": "（完整正文，不截断）",
  "contentBytes": 512,
  "wouldHaveExecuted": true,
  "reason": "observed"
}
```

**为什么存完整正文**：观察档唯一的价值就是让人判断她写得对不对。给全文，让人自己看，程序不去用正则或结构化字段猜自然语言。

**轻量定长轮转（防磁盘无限增长）**：`src/agent-observations.js` 中设常量 `MAX_OBSERVATION_LINES = 200`（约几百 KB）。追加写入发现行数超阈值时，只保留最近 200 条重写文件，不引入复杂轮转库。

## 三、本机复核修正的 3 处（相对 v1.1）

### 3.1 `agent-ipc.js` 是 12 处，不是 9 处

见 1.2 表格。**这是数字修正，但方向更保守。**

### 3.2 🔴 `observed` 条目不得挤占真实 `selfNote` 队列（真 bug）

**v1.1 的漏洞**：它说 observe 条目记进 `memory.data.selfNotes` 并标 `source: 'observed'`，靠 `drained` 标记清理。但队列有两个地方会**无差别丢最旧的**：

```js
// src/memory.js:1217  addSelfNote()
if (this.data.selfNotes.length >= SELF_NOTE_MAX_QUEUE) this.data.selfNotes.shift();

// src/memory.js:290  加载路径
.slice(-SELF_NOTE_MAX_QUEUE);   // 上限同 addSelfNote：超出丢最旧
```

而 `SELF_NOTE_MAX_QUEUE = 8`（`memory.js:102`）。

**后果**：observe 档连续产条目（她挂机时反复想写）会把**真正写成的 `selfNote` 挤掉**——那些是已经落盘、已经铸进自传的正式条目，被一个「没写成的念头」顶掉。

**这不该发生。观察档的东西优先级必须低于真实留痕。**

**修法（二选一，我推荐 A）**：

**A. 独立队列（推荐）**

```js
// 观察档条目进独立数组，与真实留痕物理隔离
this.data.observedNotes = [];   // 上限 OBSERVED_MAX_QUEUE = 3
```

好处：
- 物理隔离，不可能挤占
- `selfNotesToEngrave()` 完全不用改（它只看 `selfNotes`）
- 清理逻辑独立，不碰 D-24 的铸造幂等

代价：`_drainSelfNotes()` 要多读一个队列（或干脆不读，见 3.3）。

**B. 淘汰时优先丢 `observed`**

```js
if (this.data.selfNotes.length >= SELF_NOTE_MAX_QUEUE) {
  // 优先淘汰观察档条目，保护真实留痕
  const idx = this.data.selfNotes.findIndex(n => n && n.source === 'observed');
  this.data.selfNotes.splice(idx >= 0 ? idx : 0, 1);
}
```

好处：改动小。
代价：两处（`addSelfNote` + 加载 `.slice()`）都要改，且加载路径的 `slice` 逻辑要重写成「保留真实、丢观察」，容易漏。

**推荐 A。** 隔离比优先级更可靠——优先级逻辑在两条路径上都要写对，隔离只需要建一个新数组。

### 3.3 observe 档**不回流给她**

**v1.1 的设计**：observe 条目以 `source: 'observed'` 记进 `memory`，下轮注入「你心里浮现过这些念头（只留在了心底，没有放到桌面上）」。

**我不同意。**

**理由（按强度排序）**：

1. **观察者效应。** observe 档的整个意义是「让我先看看她在没人时会怎么做」。如果她知道「我的念头被记录了但没写成」，她的行为就变了——这正好毁掉观察本身。**要观察，就不能让她知道被观察。**

2. **她会试图补救。** 模型看到「你想过但没写成」，很可能理解成「上次没完成」，下一轮执着重试同一张便签。v1.1 自己也在 2.4 里承认了这个风险（所以改了措辞）——但改措辞只是缓解，不消除。

3. **她会学会「想想就够了」。** 另一条更糟的路径：如果「想过 = 被记录 = 被看见」，那落盘这个动作就没有额外收益了。这会**削弱她做事的动机**。

4. **observe 是给你看的，不是给她看的。** 记录的目的是让你判断「她判断得对不对」，不是让她反省。这两件事的对象不同。

**结论**：`observe` 档 **不调 `memory.addSelfNote()`，不注入任何回流**。

她那边就是「这次没写成」——**和一次普通的拟稿失败在体验上完全相同**，而那个已经有既定处理（`main.js:469` 决策 4：写失败不告诉她）。

> ⚠️ **这条要你最终拍板**。如果你希望她知道自己「想过」，那是另一种产品选择——但那时 observe 就同时变成了「内心独白记录」，语义会变重。

**附带好处**：3.3 一旦成立，3.2 的独立队列就**更简单**了——`observedNotes` 只给你读，不进 `memory.data` 的注入链路，连 `drained` 标记都不需要。

## 六、为什么砍掉「总监外壳」，回归「记忆地基」

1. **「总监」是一段关系，不是一个文件格式或能力层。** 她得先知道上次提出了什么、你为什么拒绝、后来改成了什么，才谈得上帮你把控方向。这些全是**记忆（动作史 + 回声）**，不是 JSON 工单模板。

2. **现有 `workspace.write` 已经够写方案了。** 1.1 实测证明平铺的 `.md` 走现有通路完全能落盘。等记忆地基打好后，初澜直接用现有能力在 `LifeSandbox/` 下写一份平铺 `.md` 即可，**根本不需要突破五道安全闸门去加新 Capability**。

3. **DeepSeek 那套 Mandate / Ticket 是为「一个团队一个仓库」设计的。** 初澜没有 Source、没有 Thread、没有多人协作。硬套会得到一个更复杂、但不知道解决什么的东西。（参考：`docs/PROPOSAL-SUPERAGENT-LESSONS.md`）

## 七、通往「总监」的正确演进顺序（反过来走）

| 阶段 | 核心事项 | 状态与预估 |
| :--- | :--- | :--- |
| **第 1 步（本版）** | **`observe` 观察档** —— 建立「她自发做事」的可观测性与安全试验田 | 本方案，~300 行，零安全边界改动 |
| **第 2 步（紧随）** | **动作史投影** —— 让她读得到自己做过什么 | 约 100~150 行，与第 1 步一起构成地基 |
| **第 3 步（等数据）** | **`refused` 回声** —— 积累真实拒案数据后，让她记得判断结果 | 待 `refused_by_subject > 0` 后启动 |
| **第 4 步（水到渠成）** | **轻量方案共创** —— 复用现有 `workspace.write` 平铺输出 `.md` | 地基稳固后再谈 |

> **第 1 步与第 2 步有协同**：`observe` 产生的记录，正好是动作史投影要读的数据源之一。
> 所以 2.3 的记录格式应按投影的需要设计，不要各做各的。
