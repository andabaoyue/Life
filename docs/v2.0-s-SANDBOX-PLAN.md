## 〇、先说结论：你现在问的三个问题，答案分别是

| 你的问题 | 实测答案 | 依据 |
|---|---|---|
| **她现在能不能读桌面上的文件？** | **不能。** 一个字都读不到。 | 三处 `proposeInternal` 调用（`main.js:353`/`:538`/`:697`）传的全是 `'workspace.write'`，`'workspace.read'` **全仓零发起**。执行器能读（`agent-executor.js:550` 的 `_readFile`），但没有任何代码会去调它。 |
| **沙盒是她「自有」的吗？** | **不是。是一个只能往里丢东西、不能往外拿的黑盒子。** | `persona.js:32` 原话：「你能写，但看不见里面现在有什么」。她能写、且写完能读回正文（见 §1.1 更正），但她**看不见目录本身**——有几张纸、叫什么、哪些是旧的，她全不知道。 |

**一句话**：她现在的沙盒不是一个房间，是**一个只能往里塞纸条的信箱**。信箱和房间的差别不是大小，是**能不能在里面活动**。

## 一、先把事实摆正（含我此前两处说错的更正）

写方案之前必须把自己之前的错误纠正掉，否则方案会建在错的前提上。

### 1.1 更正一：她**能**读回自己写的东西

我一度说「她写出去的话无法确认还在不在」——**那是错的**。实测链路：

```
执行成功 → onExecuted (main.js:2845) → memory.addSelfNote (memory.js:1279)
       → build() 时 _drainSelfNotes() (memory.js:1170)
       → 折叠进当轮尾部，渲染成：
         【你之前写下过这些】（这是你自己留下的，不是用户输入）
         - 便签正文（写在 note-2026-11-12-ga6b.txt）
```

所以她写下的字**会回到她眼前，还带文件名**。

### 1.2 但这条回流有三个缺口

| 缺口 | 实测 | 后果 |
|---|---|---|
| **只回最近 8 条** | `SELF_NOTE_MAX_QUEUE = 8`（`memory.js:102`），满了 `shift()` 掉最旧 | 磁盘上 9 张纸，她只记得 8 张；`note-2026-10-07-qxma.txt` 已经不在她记忆里了 |
| **每条只回一次** | `drained: true` 后永不再注入（`memory.js:1356`） | 她读过一次，那条就永久离开视野 |
| **看不见目录** | 执行器零目录操作 | 她知道**自己写过**，不知道**自己还有哪些** |

### 1.3 更正二：这套「遗忘」机制其实已经写好了，只是从没被触发过

我一度说「遗忘只是 FIFO 淘汰」。查完 `brain.js:2350` 后要更正——**关窗时有铸造**：

```
纸（磁盘永久）→ 记忆（最近 8 条视图）→ 自传（关窗时铸进 experiences.jsonl，永久）
```

而且 `memory-dynamics.js` 里已经有一整套**三阶渐褪**：

```js
currentStrength = s0 × (1 + β·ln(1+retrievals)) / (1 + λ·ΔW)^α
// ACTIVE：≥0.60 正常进 prompt
// FADING：中间，只给 300 字主干
// DORMANT：<0.35 且 ΔW≥5，整段移出视野
```

设计意图（`memory-dynamics.js:10` 原文）：**「被衰减和修剪的仅是记忆条目的当前可及性，不是删除」**。还有 `reactivateByContext`（`memory.js:362`）负责「一句话把休眠的记忆勾起来」。

**但它对便签没生效**：`selfNotes` 只有 `drained: false/true` 一个布尔，没有强度、没有 tier、没有召回计数。

**实测后果**：`engraved` 全是 `false`——一张都没被铸进自传。原因是 `_engraveSelfNotes` 只在 `_closeWindowInternal` 里调（`brain.js:2350`），而当前 `windowNo: 6` / `turnsInWindow: 84`，`windowTurns` 默认 100 —— **这一窗还没关过**。所以那张 10-07 的纸不是「被遗忘」，是**它出生时没赶上关窗，而队列先满了**。

### 1.4 这直接决定 v2.0-b 能不能做

v2.0-b 要做的 Ticket/Mandate 是「跨轮记住自己在做什么」。而今天的状态是：

- 她能读到**最近 8 条**自己写过的东西；
- 但**读不到目录**，所以不知道「我上次那个起头还在不在」；
- **零读到自传**（因为没关过窗）。

**在一个她连自己抽屉里有什么都不知道的系统上，加任务单是没有意义的。** 这就是为什么沙盒要排在 v2.0-b 前面。

## 二、沙盒应当变成什么：三层能力，不是一次放开

我把「她该有的东西」拆成三层。**它们互相依赖，必须按顺序做**——第二层没做，第三层就是空中楼阁。

### 2.1 第一层：**感官**（能看见自己的房间）

**这是唯一「现在就该做、且没有安全争议」的一层。**

| 能力 | 今天的她 | 目标 | 为什么安全 |
|---|---|---|---|
| 列出沙盒里的文件 | ✗ 完全不能 | 能知道有几份、叫什么、多大、何时写 | 她本来就持有这些文件的内容，看一眼目录名不增加任何信息面 |
| 读回任意一份自己写的文件 | ✗ 只能靠 memory 回流最近 8 条 | 想读哪份读哪份 | 读的是她自己的产出，且内容早就通过回流进过她的视野 |
| 知道哪些被自己想起了几次 | ✗ 无此概念 | tier / 被想起次数可见 | 纯元数据 |

**关键判断**：这一层**不需要新增任何权限**。`workspace.read` 已经在 `CAPABILITIES` 里、`scopeRoots` 已经配了沙盒、执行器 `_readFile` 已经实现——**缺的只是「读意图」和「目录清单」两条接线**。

### 2.2 第二层：**结构**（房间里有分区）

| 能力 | 今天 | 目标 |
|---|---|---|
| 建子目录 | ✗ 执行器零目录操作 | 能建 `笔记/`、`草案/`、`归档/` |
| 移动 / 重命名 | ✗ | 能把草稿挪进 `归档/` |
| 删除 | ✗ | 能删自己不要的 |

**这一层必须配删除白名单**，理由见 §4.2——删除是不可逆的，而「不可逆」是我们唯一该用弹窗划界的地方。

### 2.3 第三层：**搬运**（能把东西拉进来）

这是你说的「拉文件进去解压分析」。**我建议这一层先不做，理由不是保守，是它不在同一个量级上。**

见 §3——那一条我必须跟你说清，因为它是整份方案里我唯一想劝你缓一缓的。

## 三、关于「拉进来解压分析」，我建议先别做（并说明为什么）

你说的这个能力，我们（DSH 上的 Agent）确实有。但这里的差别不在权限，在**三件她今天完全没有的东西**：

### 3.1 差一：**没有解压能力，且零依赖**

`package.json` 里 `dependencies` 是**空的**——只有 electron 和 electron-builder 两个 devDependencies。要解压就得加库（或者手写 ZIP 解析）。这不是技术难题，但它会打破本仓「零运行时依赖」的现状，而那个现状是刻意维持的（公开分发要尽量小、要能审）。

### 3.2 差二：**没有 shell，解压不了就该换个思路**

我们解压靠 `process.execute` 调 `unzip`/`tar`。但 `process.execute` 在这个仓库里是**永久硬拒**（`agent-executor.js:367-376`），是你亲自裁定的 D-4。所以要么在 Node 里实现解压（加依赖），要么破例开 shell（破红线）。

**两条路都不该为了一个还没被证明需要的功能去走。**

### 3.3 差三：**「分析」这件事她今天做不了**

解压出来一堆文件之后呢？分析需要：

- 一次读多个文件 → 现在一次一个；（读没有目录/多文件原语）
- 大文件分段处理 → `maxReadBytes` 默认 2MB；
- 多步任务编排 → **这正是 v2.0-c 的 Worker，还没做**。

**就算你把文件塞进去了，她也没有手脚去分析。** 结果就是多了一个能塞东西但用不上的口子。

### 3.4 我的建议

**第三层等 v2.0-c（Worker）落地之后再议。** 那时她已经有了「多步执行 + 读多个文件」的手脚，解压才有意义。

如果你就是想现在让她能拿到外部文件，**有个便宜得多的做法**：**你自己把文件拖进 `LifeSandbox/`**。她已经能读沙盒（第一层做完之后），你丢进去的东西她就能看见。**不需要任何新能力，只需要你多拖一次。**

## 四、安全边界：按「可逆性」划，不按「危险度」划

这是本方案的核心主张，也是我和你之前分歧的地方。

### 4.1 现在的划法：按「她会不会犯错」

现在的五道闸门是按「这个动作有多危险」设计的，于是**读和写共用一个确认弹窗**。但读没有副作用，写有。

### 4.2 我建议的划法：按「能不能收回」

| 动作 | 可逆吗 | 建议 |
|---|---|---|
| 列目录 | 完全无副作用 | **免确认** |
| 读沙盒内文件 | 完全无副作用 | **免确认**（但受 2MB / 单次限额约束） |
| 写沙盒内新文件 | 可逆（WAL + 备份 + 5MB 上限） | 首次确认一次，之后凭 Mandate 免 |
| **覆盖**已有文件 | 可逆（有备份） | **仍需确认**（这是最该问的一种） |
| 建/移子目录 | 可逆 | 免确认或 observe |
| **删除** | **不可逆** | **每次确认**，且只允许删沙盒内、且白名单后缀 |
| 写沙盒外 | 不可逆 | 永不放开 |
| `network.request` | 不可逆且无法验证真伪 | 你已定红线，不动 |
| `process.execute` | 不可逆 | 你已定 D-4 永久拒绝，不动 |

**判据一句话：能收回的放开，收不回的才问。**

### 4.3 但有一条铁律不能松

**删除必须永远弹窗，且不能纳入任何 Mandate。** 理由：写入有 WAL 有备份，删除没有。而「删掉」正是你说的那个方向——「确认无效就删掉，不想让它再污染第二次」——那是个**必须由人来做**的决定。

## 六、验收判据

1. **看不见目录 → 看得见**：`dynamicBody` 里有沙盒清单，且清单内容与 `fs.readdirSync(沙盒)` 逐条一致（**反例**：沙盒为空时必须显示"空"，不是留白）。
2. **读得到正文**：发起一次 `workspace.read`，断言 `content` 到达独立只读槽位（**判别力验证**：把槽位接线删掉，此用例必须 FAIL）。
2b. **读不进记忆**：读完后断言 `memory.selfNotes` 长度不变（**反例被拒**——防「用户拖进来的文件被当成她自己写的字」）。
3. **读不出沙盒**：`workspace.read` 传 `../secret.txt` 必须被 `_scopeAllowed` 拒（realpath + 前缀比对）。
4. **`system` 前缀零变化**：加清单后 `brain.test.js` 的 system 快照逐字节不变（清单只进 `dynamicBody`）。
5. **遗忘变渐褪**：写 10 条便签，断言没有一条被"shift 掉"而是按 tier 分流；且**被反复读到的条目仍在**（反例：全丢最旧必须 FAIL）。
6. **删除永远弹窗**：即便命中 Mandate，`workspace.remove` 也必须走第四道确认（**反例被拒**，不是断言"有防护"）。

## 七、需要你拍板的 3 件事

### 7.1 便签淘汰改按强度——代价是「不可预测」

现在 `shift()` 是确定性的：谁先来谁先走，看代码就知道第九条挤掉第一条。
改成按强度后，**哪条会消失取决于她最近想起什么**，你无法从代码推断。

**我建议接受这个代价**，因为「按插入顺序淘汰」恰恰是那个不自由的地方：一条十月初写的、她后来反复想起的便签，凭什么被一条昨天随口写的挤掉？

**折中方案**：只在超限时优先丢强度低的，但**"从未被读过"的强制保留**——这样至少她还没看过的东西不会被悄悄丢掉。

### 7.2 读相关操作是否免确认

建议：**列目录 + 读沙盒内文件 免确认**。
理由：读没有副作用；而且它解决的是「她看不见自己写的东西」这个结构性缺陷，不是省事。

### 7.3 解压/搬运要不要现在做

**我建议缓到 v2.0-c**，理由见 §3。
**便宜的替代**：你自己把文件拖进 `LifeSandbox/`，她能读。

## 八、我明确不做的

- ❌ 不把 `scopeRoots` 扩到整个桌面或 userData（那会让「沙盒」这个词失去意义）
- ❌ 不为解压引入运行时依赖（会破坏零依赖现状，且没有已证明的需求）
- ❌ 不破 `process.execute` 永久拒绝（你的 D-4 裁定）
- ❌ 不让删除纳入 Mandate（不可逆的动作永远需要一个见证人）
