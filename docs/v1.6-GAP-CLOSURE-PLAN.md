## 1. v1.6-a：观察日记长度护栏修正

### 1.1 问题（实测）

`src/brain.js:2824`：

```js
if (text.length < 30 || text.length > 400) return null;
```

**这不是截断，是整篇丢弃。** 她写超过 400 字时，日记直接 `return null`，一个字都不留下。

而 `maxTokens: 400`（`brain.js:2811`）是 **token** 上限，DeepSeek 中文约 1 字 ≈ 0.65 token，**实际允许写到约 600 字**。

所以真实情况是：

```text
提示词说「最长 400 字」
  → 她如果听话，写 300~400 字 → 通过
  → 她如果写嗨了，写 450 字 → 【整篇丢弃】
```

**风险**：日记功能上线后，可能经常「什么都没留下」，而日志里没有任何痕迹（`return null` 是静默的）。

### 1.2 修正方案

**方案 A（推荐）：超长时截断保留，不丢弃**

```js
// 判据 2：篇幅护栏。过短丢弃（没内容），过长截断保留（不浪费她写的东西）
if (text.length < 30) return null;
const finalText = text.length > 400
  ? truncateFadingText(text, 400)   // 复用 v1.2.x 的句界截断纯函数
  : text;
```

**为什么复用 `truncateFadingText`**：它已经实现了「在句界处优雅截断 + 无标点安全回退」，v1.2.x 交付并测过。**不要另写一个截断函数**——那是第二套实现，迟早漂移。

`truncateFadingText` 在 `src/memory.js` 已导出（`module.exports = { Memory, estimateTokens, truncateFadingText }`）。

**方案 B（备选）**：把 `maxTokens` 提到 800，护栏提到 600。**不推荐**，因为治标不治本——她仍可能写超。

### 1.3 验收判据

```text
① 写 30 字 → 通过
② 写 29 字 → 丢弃（过短）
③ 写 380 字 → 原样通过（不截断）
④ 写 500 字 → 截断到 ≤400 且以完整句结尾，返回非 null
⑤ 写 500 字无标点 → 硬截 400 + 省略号，返回非 null
```

**断言 ④ 是核心**：修复前它会 `return null`，修复后必须返回内容。

## 2. v1.6-b：INT-01 剩余两个模块的处置

### 2.1 现状（审计记录核实）

`research/security/audits/v0.9.8/SANDBOX-SECURITY-AUDIT.md:245`：

```text
[INT-01] P4 子系统已实现+已测但未接入生产请求路径
- Severity: High（研究完整性/预期落差）
- Status: CONFIRMED
- Component: provider-routing.js · generation-attempt.js · circuit-breaker.js · brain.js
- Impact: 「fallback 受 outputYielded/cost/privacy/budget 约束」
          「circuit breaker」「一次调用一 Attempt」等 P4 契约真实 runtime 不生效
```

**v1.5-a 只解决了 `circuit-breaker.js`。** 剩余两个：

| 模块 | 行数 | 生产引用 | 提供的契约 |
| :-- | --: | :--: | :-- |
| `provider-routing.js` | 102 | **0** | Routing Contract 四字段（selectedProvider / fallbackProvider / attemptedProviders / fallbackReason） |
| `generation-attempt.js` | 99 | **0** | Attempt/Result 轨迹（一次调用一 Attempt，fallback = 新 Attempt） |

### 2.2 ⚠️ 关键前提：v1.5-a 已经做了一套平行实现

**这是本项最重要的判断依据。**

v1.5-a 新增的 `fallback-adapter.js` **自己实现了回落逻辑**，但它**不产生 P4 契约的 Attempt 轨迹**。也就是说现在有两套东西：

```text
P4 契约（provider-routing / generation-attempt）—— 有测试，无生产引用
v1.5-a 实现（fallback-adapter）        —— 有生产引用，无 Attempt 轨迹
```

**所以有两条路，必须选一条，不能继续保持现状**（现状最糟：两套并存，审计项更复杂）。

### 2.3 两条可选路径

**路径 A：把 Attempt 轨迹接进 fallback-adapter（推荐）**

- 在 `fallback-adapter.js` 里调用 `generation-attempt` 记录每次尝试
- 用 `provider-routing` 的契约字段填遥测
- **不引入第二套回落逻辑**，只是给现有实现补轨迹
- 工作量：中等（要理解两个模块的 API）

**路径 B：明确降级为「架构储备，不计划启用」**

- 在 `README.md` 与审计文档里写清：「P4 Attempt/Routing Contract 为架构储备，当前由 `fallback-adapter.js` 提供等效能力，P4 契约不启用」
- 把 `provider-routing` / `generation-attempt` 的测试标注为「契约测试，非生产门禁」
- 工作量：小（纯文档）

**DSH 建议：先做路径 B，把审计状态澄清**；等真正需要「完整尝试轨迹」（比如做成本归因看板）时再做路径 A。

**理由**：当前没有消费者读 Attempt 轨迹。接了也是死数据，和现在没接本质上一样，只是审计更漂亮。**不如诚实标注**。

### 2.4 若选路径 A 的实施要点

查看两个模块的实际导出：

```text
generation-attempt.js —— 需要 createGenerationAttempt / markAttemptFailure / createGenerationResult
provider-routing.js  —— 需要 evaluateFallback 等约束判定
```

🔴 **必须先读源码确认 API 形状**，不要假设。本仓已经踩过「按名字猜 API」的坑（v1.2 时期的 `@sampleDormantRecall` 幻觉）。

### 2.5 验收判据

**路径 B**：
```text
① README 中 INT-01 声明更新为「已澄清：P4 契约不启用，由 fallback-adapter 提供等效能力」
② 审计文档追加处置结论
③ 无代码改动，门禁全绿
```

**路径 A**：
```text
① 一次成功调用产生 1 个 Attempt
② 回落时产生 2 个 Attempt（primary 失败 + fallback）
③ Attempt 轨迹写进遥测，且不含 apiKey
④ 原有 51 项 v15 测试仍全绿（不破坏现有行为）
```

## 3. v1.6-c：通路 B 接通（可选，优先级最低）

### 3.1 现状

`main.js:162` 的 `tryBuildProposalFromIntent` 仍是显式 `return null`。

D-12 的注释说明了原因：

> 这类意图**只有 scope（文件名），没有 content（要写什么）**。建出来会是一个空内容的案。

### 3.2 但前提已经变了

D-12 定的正解是「内容来自**会话记忆提炼**」。

**而 v1.4-a 已经给 `askForSelfNote` 接通了素材供给**（自我投射 + 生理体感 + 清洗后的近期对话 + 上次便签）。

**这个能力其实已经具备了**，只是没有接给通路 B。

### 3.3 但有三个必须先想清的问题

1. **谁来触发?** 通路 B 是「用户说『你把这个写下来』」的场景，和 `wantToLeaveSomething`（她自己想写）不同。**触发判据在哪？** `_pendingAgentIntent.shouldPropose` 现在谁设置？
2. **内容该是什么?** 「会话记忆提炼」会让它变成一份摘要——**那是她写的，还是程序整理的？** 边界必须说清，否则就是程序代拟。
3. **和通路 A 的关系?** 通路 A 是「她自发留便签」，通路 B 是「用户让她写」。**两者的 prompt 与护栏应该完全不同**，不能复用。

**DSH 建议：v1.6-c 暂不做。** 理由：

- 它是**唯一真正需要新设计的**（其余两项都是收口已有东西）
- 没有用户需求驱动的证据（有没有人真的让初澜写文件？）
- 做错了会产生「程序代拟她的文字」，那比不做糟糕得多

**建议归档**，重新激活条件：用户实际提出「让她帮我写个文件」的需求。
