## 〇、一句话定位

**保留初澜「数字生命与陪伴」的产品灵魂与五道安全闸门不动，借用 DeepSeek 2026-10-31 开源的 Super-agent（`dsh-superagent-prototype`）工程骨架，把初澜从「散落单次钩子驱动的被问工具」，升级为拥有统一决策路由、跨轮授权/任务生命周期、声明式能力注册与隔离后台执行的自主 Agent。**

核心取舍只有两句话：

1. **借它的决策、授权、生命周期与调度工程；**
2. **坚决拒绝它的「最小化占用人类注意力」冷酷过滤哲学，以及团队/云端基础设施外壳。**

## 二、现状诊断：为什么 `v1.9.0` 的 Agent 底座撑不起下一阶段

以下问题全部来自本仓现行代码实测：

| 现有痛点 | 代码实测证据 | 对初澜进化的阻塞 |
|---|---|---|
| **1. 没有统一决策路由，三条触发靠散落钩子与「巧合安全」运转** | `main.js:1273-1314` 中，`tryBuildProposalFromIntent()`（通路 B）与 `maybeAskForSelfNote()`（通路 A）在非 proactive 分支读**同一个** `brain._pendingAgentIntent`；当前全靠「首次 await 前同步置 null」＋「`agent-intent` 对象恰好没有 `kind` 字段」两条**巧合**才没重复消费（`main.js:1285-1297` 注释已自承危险）。观察日记则另挂在 `res.windowClosed` 后（`main.js:1246`）。 | 每多一种行为都要在 `main.js` 再挖一条旁路，判定逻辑分裂在 `trigger.js`、`agent-intent.js` 和 `main.js` 三处，无法统一做优先权、冲突仲裁或成本控制。 |

| **3. 能力（Capability）硬编码分散，扩一个能力要动 6 个文件** | 实测 `src/agent-ipc.js` 中 `workspace.write` 字面量出现 **12 处**（行 `29, 215, 226, 291, 334, 378, 468, 473, 484, 495, 506, 743`）：**8 处是代码、4 处是注释**（`29, 226, 334, 468`）。8 处代码里，5 处是真判定（`215, 291, 378, 473, 743`），3 处是审计字段赋值（`484, 495, 506`，与 `473` 同属一个 `if` 分支）。还要同步改 `agent-interfaces.js:40, 84`、`agent-executor.js:54` 执行分支及 `ui-agent-confirm.js:46`。 | 虽然 `agent-interfaces.js:110` 的 `CapabilityRegistry` 早已预留 `register()`，但实际链路完全没走元数据驱动；`agent-executor.js` 已有 `_readFile`（`:550`），而 `agent-intent.js:69-77` 明确零读意图，**读能力被锁死在孤岛上**。 |
| **4. 重任务与主对话无隔离，缺乏标准进度回报通道** | 通路 B 用 `void tryBuildProposalFromIntent()` 在主进程发起裸奔异步单次调用（`main.js:1298`）；通路 A 内部是 `void (async () => {...})()`（`main.js:444`）。**全仓没有任何任务状态机**（`pending/running/blocked/ready`），降级失败（如 `S-3` 沙盒不可用）也没有运行时告知通道（[`PENDING-TASKS.md §8.3`](PENDING-TASKS.md#L365-L372)）。 | 未来只要引入「先读几份旧笔记 → 归纳 → 拟稿 → 落盘」这类多步自主动作，现行裸奔 `void` 调用既不可观测、也不可暂停/恢复。 |

## 三、产品哲学红线：借框架，不换魂

DeepSeek Super-agent 的 [`000-philosophy.md`](PROPOSAL-SUPERAGENT-LESSONS.md#L149-L166) 核心信条是：

> *Take as little human attention as possible, and give as much value as possible.*（只在人类必须决策或能直接用产出时开口。）

**这条不能套到初澜身上**，理由有三：

1. **「没用」往往正是陪伴价值本身**：她挂机 120 分钟后留的一句便签、重逢时一句感叹，按工程效用衡量全都是「消耗注意力的低价值输出」，按生命陪伴衡量却是本体。
2. **交互尺度不同**：DeepSeek 面对的是研发团队 7×24 多仓库并发；初澜是**个人桌面单伴侣**，不能搞出企业工单机器人那套冷冰冰的 SLA 汇报口吻，也不能无节制后台并发烧用户自己的 API 额度。
3. **现行防骚扰与反表演铁律必须原样保留**：
   - `trigger.js` 的三道防骚扰铁律（睡眠闸门 / `COOLDOWN_MS` / `spokenDuringIdle` 与 `selfNoteDuringIdle` 单次刹车）不动；
   - `persona.js` 反表演红线（不虚构寂寞、不说不知时间的话）不动；
   - 前缀缓存不变式（**`system` 提示词绝对静止，一切运行时态/任务态注入走 `memory.build()` 当轮尾部或独立旁路**）不动；
   - 五道安全闸门与硬件红线不动：`network.request` 仍硬封禁（`agent-interfaces.js:101-107`）、`process.execute` 仍入口永久硬拒（`agent-executor.js:32-38`）、写盘仍强制沙盒 `realpath` 校验 + 扩展名白名单 + SHA-256 内容快照 + WAL 事务。

## 四、Life v2.0 架构设计（四层骨架）

整体结构从「散落调用钩子」收敛为 **「感知/触发源 → 统一决策路由（Router）→ 生命周期管理（Mandate / Ticket）→ 注册化能力与受控执行/Worker」**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        输入事件与触发源（不直接建案）                       │
│   ① 用户对话结束    ② TriggerEngine 挂机/戳弄    ③ 关窗(windowClosed)     │
└──────────────────────────────────┬──────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────┐
│             ① 统一决策路由（src/agent-router.js，新核心）                  │
│   阶段 A 程序快筛：总开关 / 睡眠 / 冷却 / 预算 / 观察档(off/observe/auto) │
│   阶段 B 模型/规则慢判：统一输出 { decision, strength, capability, ... }  │
│          decision ∈ accept | stop | ignore | unavailable                │
│          strength ∈ explicit | inferred                                 │
└───────────────┬─────────────────────────────────────────┬───────────────┘
                │ accept（进入生命周期）                     │ stop / ignore
                ▼                                         ▼
┌───────────────────────────────┐             ┌───────────────────────────┐
│ ② Ticket + Mandate 持久层      │             │ 仅记审计 / 观察日志         │
│   agent-tickets.json (原子写)  │             │ （绝不进 memory.history）   │
│   · Ticket: open↔paused↔ended │             └───────────────────────────┘
│   · Mandate: 会话/范围授权凭证 │
└───────────────┬───────────────┘
                │ 派发执行或挂起待用户确认
                ▼
┌─────────────────────────────────────────────────────────────────────────┐
│       ③ 声明式能力注册表 + 轻量 Worker 通道（守住既有五道安全闸门）          │
│   · CapabilityRegistry 元数据驱动（消除 agent-ipc.js 12 处硬编码）        │
│   · 单发直写（selfNote 等）继续走现有执行器免/需确认分支                    │
│   · 需多步读写的重任务走单并发 Worker 隔离运行 → Report 回传主对话尾部      │
└─────────────────────────────────────────────────────────────────────────┘
```

### 模块一：统一决策路由（`src/agent-router.js`）

把分散在 `main.js`（通路 A `maybeAskForSelfNote`、通路 B `tryBuildProposalFromIntent`、观察日记 `maybeAskForObserverJournal`）的分支全部收口进一台只做「评估与分派」的 Router：

1. **统一决策输出结构（对齐 `policy.ts` 核心抽象，贴合本地需求）**：
   - `decision`: `'accept' | 'stop' | 'ignore' | 'unavailable'`
   - `strength`: `'explicit'`（用户明确提出）/ `'inferred'`（挂机、关窗、语境推断）
   - `capability`: `'workspace.write' | 'workspace.read' | ...`（不再默认写死 `'workspace.write'`）
   - `mode`: `'off' | 'observe' | 'auto'`（复用 `v1.9.0` 已有 `getCapabilityMode`）
2. **两级过滤（程序快筛 + 模型慢判）**：
   - **L1 程序快筛（零 Token 成本）**：先查 `agentTriggerEnabled`、沙盒是否可用（顺带解决 `S-3` 运行时告知）、`mode === 'off'`、预算余额、既有防骚扰刹车与活跃 Ticket 冲突。**快筛不过，直接不调用任何 LLM**。
   - **L2 慢判与拟稿分离**：只在 L1 放行时才进入模型判定/拟稿；彻底消灭 `main.js:1285-1297` 靠字段缺漏维持的「巧合安全」，同一轮对话至多进入一次仲裁，不会由两条旁路抢同一个意图字段。
3. **保留温度的 `inferred` 处理规则**：
   - 自发情感类表达（如 `selfNote` / `observerJournal`）继续保留既有 `auto` 豁免权，不因引入 Router 而倒退成必须逐次弹窗。
   - 其它非豁免的 `inferred` 行为严格遵循 `observe` 先观察、再由用户决定是否切 `auto`。

### 模块二：轻量 Mandate + Ticket 生命周期（`src/agent-lifecycle.js`）

这是从「一次性建案工具」跨向「连续自主 Agent」的关键补块，全部用 `src/atomic.js` 原子写持久化到 `%APPDATA%\Life\agent-tickets.json`：

1. **Ticket（任务单状态机：`open ↔ paused ↔ ended`）**
   - 解决痛点：用户随口说「帮我建一个读书笔记框架，先留个头，回头聊到再往里添」，或者因内容没聊透被暂停（`stop` / 缺信息）时，不必当场丢弃或强迫写死一个半成品。
   - ⚠️ **与原型的有意偏离**：原型 `Ticket` 只有 `open → ended`，**没有 `paused`**——它把「暂停」表达成 Assignment 结束 + `waiting` Report（见 `docs/003-execution.md`「Ticket stages」表）。本方案**刻意加一个 `paused` 状态**，因为桌宠场景里「她做了一半，等你回来补一句」是高频形态，而原型的 `waiting` 语义绑定在 Worker 会话上，我们没有 Worker 常驻进程可挂。
   - **核心机制**：
     - 当一轮任务需要等待用户确认、缺少上下文或主动拆成多步时，Ticket 进入 `paused`；
     - 下次对话聊回同一主题/目标时，Router 可检索少量活跃 Ticket（只注入摘要与状态到 `memory.build()` 尾部，**不污染 `system` 前缀，不存对话全文**）将其**无缝唤醒回 `open` 续做**；
     - 用户一句话叫停（或显式关闭）即进入不可逆 `ended`（或撤销）。
2. **Mandate（作用域授权凭证——严格受限，绝不架空安全闸门）**
   - 解决痛点：目前用户想让初澜持续整理沙盒内某份文档或完成一组读+写整理动作，每写一次/每读一次都要反复点【授权】卡片。
   - **铁律边界（给安全审阅方/阿查的硬承诺）**：
     - **范围不可扩大**：Mandate 绑定创建时的 `{ policyRevision, capabilitySet, sandboxSubScope, maxWritesOrReads, expiresAt }`，且**对象冻结不可变**；一旦动作试图越出原定作用域（如换到别的目录或新能力），必须建新提案重新确认。
     - **高危能力永不发放 Mandate**：`process.execute`、`network.request` 以及任何沙盒外路径，**禁止纳入 Mandate**。
     - **执行期重检不动摇**：即使命中 Mandate 豁免第四道确认卡片，`src/agent-executor.js` 里的闸门 1（能力）、闸门 2（`realpath` 沙盒路径与扩展名）、闸门 3（会话预算 `ExecutionBudget`）、第五道事务（SHA-256 + WAL）**每次执行仍逐条重跑**。
     - **一键撤回（Withdraw）**：用户随时说“停/收回权限”或 UI 一键撤销，立即使 Mandate 失效。

### 模块三：声明式 Capability 注册表收口（清理 12 处硬编码）

在不削弱安全审计的前提下，把能力定义收敛到唯一事实源：

1. 升级 `src/agent-interfaces.js` 的 `CAPABILITY_META` / `CapabilityRegistry`：为每个能力显式声明元数据：
   - `scopeKind`（`'path' | 'command' | 'none'`）
   - `requiresContentSnapshot`（仅写类能力要求 SHA-256 内容快照绑定）
   - `allowExemptProposalSources`（哪些主进程可信来源允许免逐次确认）
   - `allowMandate`（是否允许纳入短期/作用域 Mandate——例如只读 `workspace.read` 与限定范围内的 `workspace.write` 可按策略配置，系统级永久 `false`）
   - `hardDenied`（如 `network.request` 保持硬死锁）
2. 消除 `src/agent-ipc.js` 的 **12 处** `workspace.write` 字面量（8 处代码 + 4 处注释），统一改查注册表元数据与守卫器。⚠️ **注释里那 4 处也要跟着改**：本仓纪律是注释即规格，留着一句写着旧能力名的注释，下一个人会照着它写出新硬编码。
3. **顺势打通 `workspace.read` 读意图通道**（解除 `agent-intent.js:69-77` 的「执行器能读但决策层从不产读意图」断层），让初澜在写之前能真正先读自己以前记过的沙盒文档。

### 模块四：单并发隔离 Worker 与非阻塞回报流（`src/agent-worker.js`）

专门承接「先读 → 归纳/整理 → 产出草稿」等不适合塞进单轮聊天回复里的较重任务：

1. **为什么严格限制「单并发（concurrency = 1）」而不是多线程 Worker 池**：
   - 个人桌面端使用的是用户自己的 API Key 与本地磁盘。并发多 Worker 既容易撞 Rate Limit、烧干预算，也容易在单份 `LifeSandbox` 文件上制造写竞争。
   - **单并发队列 + 独立 Step 预算帽**（单次 Worker 任务最多 N 步、超时自动退回 `paused` Ticket）是最稳的工程上限。
   - ⚠️ **与原型的有意偏离（值得阿查重点看）**：原型**允许配置并发上限**，并且额外给人留了一个 slot——「人的消息或状态请求可以用那个额外 slot，且优先占用下一个空位」，理由是「新工作不该把人挡在自己的 Ticket 外面」（`docs/003-execution.md`「Concurrency」）。本方案把它**收成硬性 1**，代价是：用户催「继续」时，若那唯一的 slot 正被一个长任务占着，她的回话会排队。**若裁定要保留「人优先」，就得把并发上限做成 1+1（自动任务 1、人的追问 1），而不是 1。**
2. **与主对话的关系**：
   - Worker **永不直接读写对话窗历史**，也不直接改人格状态；
   - 执行中通过结构化 `Report` 回传给 Router。⚠️ **字段对齐原型**：原型的 Report 有 6 个值 `progress / waiting / ready / blocked / failed / dropped`（`docs/001-domain.md` 词汇表）。初稿只写了 4 个，漏了 `waiting`（空闲等触发）与 `dropped`（无事可做、直接结案，且默认**不发消息**）——后者恰恰是「她判断这事不用做」这个**合法的拒绝结果**，与 `failed` 必须分开记，否则又回到「把她的决策记成故障」的老错（`main.js:314-320` 那条注释讲的就是这件事）。
   - `ready` / `blocked` 时，挂入下一轮温和唤醒提示（遵守防骚扰冷却与打字礼貌闸门，不强行打断用户输入）。
   - 顺手一并关闭 [`PENDING-TASKS.md §8.3`](PENDING-TASKS.md#L365-L372) 的 **`S-3` 沙盒不可用运行时告知缺口**（把 `agentSandboxUnavailable` 提升至模块顶层/Router 可读态，降级时不再让模型自以为能落盘）。

## 六、需要阿查与你重点审阅、拍板的 5 个裁定问题

交给阿查看时，最希望对齐以下 5 个边界决策（拍板后即可按 `v2.0-a` 起正式施工单）：

1. **Mandate 权限上限怎么定？**
   - 选项 A（推荐稳妥档）：Mandate **仅限当前会话有效**（进程重启自动失效），且只能覆盖 `workspace.read` 与「针对用户已确认过的同一目标文件/子目录」的 `workspace.write`；
   - 选项 B（更自由）：允许持久化跨重启的长期 Mandate（需增加启动时自检面板展示与一键清空）。
2. **`workspace.read`（沙盒只读）要不要免逐次确认？**
   - 目前 `agent-interfaces.js:85-89` 里 `workspace.read` 是 `requiresConfirm: true`。如果将来每次初澜想先翻一眼自己以前写的沙盒笔记都要弹确认框，多步自主整理与共创会非常割裂；是否允许在 `LifeSandbox/` 内对白名单后缀的只读动作默认放行或走 `observe → auto`？
3. **Ticket 注入对话上下文的成本预算**
   - 活跃 Ticket 摘要只能挂在 `memory.build()` 尾部以守住前缀缓存；建议硬限定单次最多注入 **3 条 `open/paused` 摘要（每条 ≤ 80 字）**，超过按最近活跃度截断。是否认可？
4. **Worker 是否强制「单并发 + 显式 Token/步数预算帽」？**
   - 建议硬锁 `maxConcurrentWorkers = 1`、`maxStepsPerTicket = 5`，超出自动转 `paused` 等用户确认继续，防止异常循环烧干个人 API Key。
   - ⚠️ 这条与「原型给人留额外 slot」相冲突，请一并裁定：**用户追问时要不要能插队？** 若要，实际是 `1 + 1`（自动 1、人 1），不是纯 1。
5. **原 `v1.9 / v2.0` 数据驱动项的归档口径**
   - `refused` 回声、轻量方案共创、生命轨迹看板、经历库分层检索全部继续保留在「条件触发池」，待后续新排期版本或独立小迭代按数据实测启动；一旦本方案拍板，即同步更新 `docs/PENDING-TASKS.md` 与 `docs/VERSION-RESCHEDULE.md` 索引。
   - ⚠️ **这条得先解决一个文档冲突**：`docs/VERSION-RESCHEDULE.md:90` 明写「**版本号不分配给 v1.9 / v2.0**。将来达标后，重新讨论用哪个号」。本方案把 `v2.0` 号拿来用，等于**推翻那条决策记录**。本仓纪律是「文档是历史记录，原结论不改，只追加处置结论」，所以拍板后必须在该文件**追加**一节说明，而不是直接改写原句。
   - 另：`docs/v2.0-PLAN.md`（原经历库检索方案）会与本文档**同号并存**，建议拍板时同步把前者标注为「条件触发，未排期」（与 `VERSION-RESCHEDULE.md:88` 给的处置一致）。
