---

## 一、目标与核心边界

### 1.1 要解决的问题

1. `src/internal-regulation.js` 目前只看瞬时静态阈值（`interactionDensity >= 40 / 60`），不区分「刚从 `62` 降到 `45`（正在恢复）」与「三步内从 `30 -> 38 -> 45`（正在逼近过载）」。
2. `src/self-ledger.js` 的 `calculateRevisionPressure()` 已算出每条自我假设的 `revisionPressure` 与 `counterEvidenceRatio`，但尚无只读汇总出口供后续主动性与认知张力层读取。

### 1.2 五条硬边界（不可退让）

1. **忽略 `assistant` 回合与无变动采样**：一次完整对话会先后触发 `user` 与 `assistant` 两次 `updateOnInteractionTurn()`，其中 `assistant` 不增 `interactionDensity`。若不加筛选，滑窗会出现 `20 -> 25 -> 25` 导致「连续两步严格上升」恒不成立。因此 `recentLoadTrail` **仅在真实刺激事件（`user` / `poke` / `drag`）且密度实际改变时采样**；密度在任意事件（含 `idle` / `windowClose` / `sleep`）下降时立即熄灭 `approachingOverload`。
2. **跨进程状态同步通道**：渲染端 `BehaviorScheduler` 只读 `internalRegulation.getState()`，`approachingOverload` 必须加入 `getState()` 返回的冻结对象，随 `main.js` 既有 `onChange = pushRegulationState` 同步。
3. **`formatPerception()` 零改动**：严守纯函数无状态契约，本轮高冲突体感**不进 Prompt**（不在第 7 窗低样本期引入口癖风险）。
4. **D-005 只读账本铁律**：`selfLedger.getRevisionTensionSummary()` 纯只读计算，绝不增删改条目、绝不写盘。
5. **只收紧不放松防骚扰铁律**：`approachingOverload === true` 时，`TriggerEngine` 只允许将 `idleNeed` 温和拉长（`1.25x`），绝不缩短 `idleNeed`，且不碰 `COOLDOWN_MS`、`CURIOSITY_THROTTLE_MS`、`spokenDuringIdle` 与 `sleepMode`；`BehaviorScheduler` 仅温和抑制外向/活跃动作权重（`0.75x`）。
