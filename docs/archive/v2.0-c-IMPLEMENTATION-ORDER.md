## 归档说明（2026-11-21）

### 为什么归档而不是继续做

本单的核心是「多步任务分流到 Ticket」。而 `v2.0-b3`（`bebb8b1`）已经把 Ticket 的**自动生产者拆到只剩一条**：

> 关窗时同会话内**超时未决的 `workspace.write` 提案** → 转一条 `paused` Ticket，标题取提案 scope 的 `basename`。

这意味着 **Ticket 池长期可能是空的**。在空池上跑 Worker，测不出任何真实行为——**是"能跑"，不是"跑对了"**。

所以顺序应该是：**先让软件跑一段时间，看是否产生真实 Ticket → 有真实数据再上 Worker。**

## 〇、一句话定位与五条纪律红线

**`v2.0-c` 是 `v2.0` 架构重构的收官模块**：在不打破现有单步直写通路（`D-10` / `D-11` / `D-27`）与五道安全闸门的前提下，落地单并发隔离 Worker（`src/agent-worker.js`），打通**「先列/读沙盒旧笔记 → 结合旧文归纳或续写 → 产出草稿提案（或主体自决放弃）」**的多步自主闭环，并通过结构化 `WorkerReport` 在下轮对话尾部做非阻塞温和回报。

### 五条绝对红线

1. **D-005 主体性铁律**：她读完旧笔记后有权决定“这回不写 / 无需重写 / 还没聊透”（即拟稿返回 `refused` 或跳过）。这必须记为合法的 **`dropped`** Report 并正常结案或挂起，**绝不能记成 `failed` 故障**，更不得逼她交差。
2. **前缀缓存不变式**：`memory.systemText()` 一字不动。`WorkerReport` 只通过 `memory.build()` 当轮尾部独立槽位一次性消费注入，空集严格返回 `''`（零空白标题）。
3. **历史纯净铁律**：Worker 绝不直接调用 `memory.append()` 写入 `memory.data.history`，也绝不把读取到的沙盒外部文件内容喂进 `memory.addSelfNote()`（遵守 `v2.0-s1` 只读隔离铁律，防止外部文件被错归成她自己写过的自传素材）。
4. **五道安全闸门与观察档零妥协**：Worker 内部发起的一切 `list / read / write` 必须全部走主进程注入的受控接口（`listSandboxTopLevel`、`agentIpc.proposeInternal` + `executeInternal`），受 `PermissionPolicy` / `ExecutionBudget` / WAL / 沙盒 `realpath` 校验约束，并严格遵守 `getCapabilityMode(cfg, cap)` 的 `off / observe / auto` 三档分流。
5. **防骚扰与打字礼貌**：Worker 在后台完成后仅写入待消费 `Report` 槽位（或针对显式请求的待确认提案广播 `agent-proposal-pending`），**绝不在用户打字期间抢占聊天气泡、打断流式响应或强行弹窗催促**。

### 坑 ①：`main.js` 既有函数体不可搬家或重构重写

`test/d27-proposal-content.test.js:539-576` 会直接用正则从 `main.js` 源码中抠出 `buildSandboxScope`、`tryBuildProposalFromIntent`、`auditProposalRefused` 的文本并用 `new Function` 运行，且 `:521-523` 断言 `tryBuildProposalFromIntent` 源码块内不得出现 `addSelfNote` 或 `selfLedger`。

- **对策**：`v2.0-c` 的 `agentWorker` 必须以**增量协作模块**接入 `main.js` 与 `src/agent-router.js`。原有单步写/记流程原封不动，只有在触发条件明确属于“需先读旧笔记再整理 / 唤醒多步 Ticket”时才路由至 `agentWorker.enqueue(...)`。

### 坑 ②：`dropped` 与 `failed` 混淆会污染主体决策倾向

对齐原型 `docs/001-domain.md` 的 6 态 `Report`（`progress` / `waiting` / `ready` / `blocked` / `failed` / `dropped`）：

- **`dropped`（主体自决无需动作/拒绝落笔）**：她在拟稿阶段基于真实状态判断“这回不用写”或“还没聊透没必要动”。对应 Ticket 正常转为 `ended`（或依原因转 `paused`），**默认静默（绝不推入异常回报，也绝不记作 `failed` 故障）**。
- **`failed`（模型调用 / 文件 I/O / 事务异常）**：是程序/环境故障而非她的意志。对应 Ticket **退回 `paused` 保留现场**，并向 `Brain` 写入一条客观 `failed` Report 留痕，避免把故障统计成「她总在拒绝」。

### 坑 ③：后台并发烧额度与写冲突（`1 + 1` 槽位模型）

个人桌面端使用的是用户自己的 API Key，且多协程写同一份沙盒目录易引发覆盖冲突与额度熔断：

- **对齐原型 `src/executor/dsh.ts` `WorkerSlots`**：采用严格 **`1 + 1` 槽位制**：
  - 后台自发或整理任务（`by: 'inferred'`）：硬锁 `maxConcurrent = 1`，同一时刻最多 1 个后台多步任务在跑；若槽位已占，新入 `inferred` 任务返回 `{ accepted: false, reason: 'WORKER_BUSY' }`（不排队堆积、不并发抢票）。
  - 用户显式发起的多步整理/续做（`by: 'explicit'`）：享有 **`+1` 优先槽位**（对齐原型「人的追问不应被后台长任务堵在门外」），总占槽上限 `maxConcurrent + 1 = 2`，主对话 `chat-send` 全程不受 Worker 占用阻塞。

### 坑 ④：死循环与大文件塞爆上下文（步数/体积/墙钟三重熔断）

多步「读 → 想 → 写」如果放任迭代可能陷入反复读文件或大文件撑爆上下文：

- **硬锁配额常量**：
  - `maxStepsPerRun = 5`（每执行一步前核检已用步数，严防死循环）
  - `maxReadFilesPerRun = 3`（单次最多挑读 3 份最相关旧文件）
  - `maxCharsPerFile = 2000`（复用 `brain.js:1170` 同口径，超出截断并明确标注原文字符数）
  - `maxWallClockMs = 60000`（单次多步任务墙钟上限 60 秒）
- **自愈约定**：任一步命中步数上限或墙钟超时，立即停止后续步骤，将关联 Ticket（若有）自动 `transition(id, 'paused', { note })` 保留断点，并发出一条 **`blocked`** Report 告知「本轮整理停在半途，待续」。

#### A.2 多步执行流水线（`runMultiStepTask`）

每一步进入前均检查 `shutdownRequested`、步数预算 `step <= limits.maxStepsPerRun` 与墙钟剩余时间 `elapsed < limits.maxWallClockMs`；越限直接走 `blocked` 自愈出口并释放槽位。

1. **Step 1 — 列目录筛选关联旧文件（遵守 `workspace.list` 档位）**
   - 检查 `getCapabilityMode(cfg, 'workspace.list')`：
     - `off`：跳过列目录，文件列表置 `[]`；
     - `observe`：记录一次观察日志（若本次未记过），不真列盘，文件列表置 `[]`；
     - `auto`：调用注入的 `listSandboxTopLevel(sandboxDir)` 获取顶层文件名/大小/修改时间，按关键词关联度与最近 `mtime` 挑选最多 `maxReadFilesPerRun`（默认 3）份候选文本文件（只取文件名，不触碰子目录外路径）。
   - 若任务绑定了 `ticketId` 且当前存在 `ticketStore`，确保 Ticket 处于 `open`（若是 `paused` 则先 `transition(ticketId, 'open')` 记入推进原因）。

2. **Step 2 — 受控读取旧文件（遵守 `workspace.read` 三档 + 隔离原则）**
   - 检查 `getCapabilityMode(cfg, 'workspace.read')`：
     - `off`：零读盘，直接进入 Step 3（仅依据现有对话与 Ticket 摘要拟稿）；
     - `observe`：针对候选文件写入 `observationLog`（`proposalSource: 'readOnly'`，不含正文）并 `memory.noteObserved('workspace.read')`，**不调用 `executeInternal`，不拿正文**；
     - `auto`：逐份对候选文件构造安全作用域（`buildReadScope(fileName, sandboxDir)`），经 `agentIpc.proposeInternal({ capability: 'workspace.read', scope, reason }, 'main', 'readOnly')` + `agentIpc.executeInternal({ proposalId })` 读取。
   - **隔离红线**：读取到的 `result.content` 按 `maxCharsPerFile = 2000` 截断并附带原文长度注释，存入当前 Worker 本次运行的局部变量 `readExcerpts`；**严禁调用 `memory.addSelfNote()`，严禁写入 `brain._pendingSandboxRead` 污染主对话下一轮**。

3. **Step 3 — 携带已读旧笔记摘录调用 Brain 拟稿**
   - 若来源为 **`explicit`**（用户明确请求整理/续写成文）：
     - 调用 `brain.askForProposalContent({ hint: task.hint, reason: task.reason, workerReadExcerpts: readExcerpts, ticketSummary: task.ticketSummary })`；
     - 在非流式 `complete()` 临时 Prompt 的当次段落中，清晰区分「`【沙盒旧文件参考摘录】（来自外部受控读取，非你自留便签，也非用户本轮原话）`」，供她结合旧文决定如何拟稿或是否拒绝。
   - 若来源为 **`inferred`**（空闲/回顾旧笔记后自发想写或延续未完事项）：
     - 先检查 `getCapabilityMode(cfg, 'selfNote')`；若为 `off`，直接终止本次拟稿并返回 `{ kind: 'dropped', silent: true, reason: 'SELF_NOTE_OFF' }`（零 LLM 消耗）；
     - 否则调用 `brain.askForSelfNote({ intentKind: task.intentKind || 'wantToLeaveSomething', workerReadExcerpts: readExcerpts, ticketSummary: task.ticketSummary })`。

4. **Step 4 — 按结果与档位分流（严格区分 `dropped` / `failed` / `ready` / `blocked`）**
   - **分支 ① 主体主动放弃 / 无需落笔**：
     - `explicit` 下 `draft.status === 'refused'`；或 `inferred` 下 `note === null`。
     - 记录审计 `auditProposalRefused(..., 'refused_by_subject')`（如属 `explicit`），若存在 `ticketId` 且合理结案，可将关联 Ticket 转为 `ended`（注明“她审视后决定无需重复落笔”）；
     - 产出 `{ kind: 'dropped', ticketId, reason: 'REFUSED_BY_SUBJECT', silent: true }`，**绝不推入 `pushWorkerReport`，绝不弹窗**。
   - **分支 ② 调用故障 / 内容不可用 / 执行报错**：
     - `explicit` 下 `draft.status === 'unavailable'`，或执行抛错/被 `PermissionPolicy` / `ExecutionBudget` 硬拒（非主体拒写）。
     - 若属 `unavailable` 写审计 `outcome: 'draft_unavailable'`；若关联 `ticketId` 未终结，将其 `transition(ticketId, 'paused', { note: '后台整理遇到障碍，留待续接' })`；
     - 产出 `{ kind: 'failed', ticketId, summary: ... }` 并调用 `brain.pushWorkerReport(report)`。
   - **分支 ③ 成功产出草稿 / 落盘完成 (`ready`)**：
     - **`explicit`**：经 `buildSandboxScope(task.hint, sandboxDir)` 拼合写路径，调用 `agentIpc.proposeInternal({ capability: 'workspace.write', scope, reason, content: draft.content }, 'main')`（**绝不传免确认戳，` proposalSource: 'user'`，强制保留 Gate 4 用户确认卡片**），成功后广播 `agent-proposal-pending`，关联 Ticket 保持 `open`（注明“已读旧文并拟好草稿，待用户确认落盘”，待 `agentOnExecuted` 执行成功后自动 `ended`），推送 `ready` Report。
     - **`inferred`（`selfNote`）**：若 `selfNote` 档位为 `observe`，按既有铁律只写入 `observationLog` + `memory.noteObserved('selfNote')`（不建案、不进 `selfNotes`、不入报告，保持与单步 observe 一致防止观察者效应）；若为 `auto`，走 `proposeInternal(..., 'main', 'selfNote', content)` + `executeInternal` 自动落盘，成功后由 `onExecuted` 自动铸进自传前队列并将关联 Ticket 结案为 `ended`，推送一条简短 `ready` Report。
