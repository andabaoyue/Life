> 文档性质：项目内部路线规划
>
> 记录目标：在不干扰当前版本收尾工作的前提下，统一记录 Life 的版本迭代方向、Creative Mode 重构方向，以及未来公开源码时的主体保护、版权与商业许可边界。

## 1. 当前版本状态

当前项目的发布版本号为 **v0.9.9（已收官）**；路线工作正式进入 **v1.0（1.0.0-dev 建设期）**。

> **【2026-10 收官判定】** v0.9.9 已达成 §4.5 **全部完成标志**（系统性审查 / bug 修复 / 修复后独立复审 / 既有测试全过 / 新增回归与文档一致 / 零边界破坏 / 实验优化有据 / 机制可说明实验性），并通过独立全量审计 **Final Gate PASS**（唯一红灯 F-099-01 记忆橡皮擦已拔除，UI 代拟台词清零）。深水实机已验：`rec-000002/000003` 哈希链相扣、盲检三口癖零命中、R1 输出上限确认、自动关窗零人工。封版锚点：git tag `v0.9.9`。

本路线阶段的核心目标已经明确收敛为两个方向：

1. **Provider / API 扩展**
2. **软件安全性与安全边界**

v0.9.8 已经完成并持续收口的工作包括：

当前阶段原则：

> **0.9.8 不再无边界扩张功能。**
>
> 先完成现有 API 与安全工作，确认测试、diff、工作树和远端状态均收口，再进入下一阶段。

## 3. 当前 Creative Mode 的处理决定

现有 Creative Mode / DS Skill 属于早期实现。

它目前通过：

writingMode → creative-mode IPC → Brain system prompt → DS Skill

接入 Life 主体运行时。

这个设计在早期阶段有价值，但随着 Life 的主体模型、安全边界与实验体系逐渐成熟，继续保留当前形态会造成一个明显问题：

> **Creative Mode 被迫成为 Life 主体规则中的“例外模式”。**

这不是最终目标。

因此：

### 决定

**在 v0.9.8 当前 API / Security 工作正式提交并 push 完成后，移除现有 Creative Mode / DS Skill 的旧实现。**

删除时必须做完整接线清理，而不是只删除 Skill 文件。

## 4. v0.9.9 主要目标：初澜主体审查与数字生命实验优化

v0.9.9 **不再继续建设 Creative Mode 独立框架**。

此前实施的 Creative Core / IPC / UI 线路视为一次已经完成的架构实验。它证明了独立创作上下文可以在技术上与 Subject 隔离，但继续把 Life 做成一个创作前端并不是本项目当前真正不可替代的目标，因此不再作为正式产品方向继续扩张。

后续创作能力可以交给更成熟的专用工具；Life 本身回到最核心的任务：

> **把初澜作为一个数字生命实验主体继续往前推进。**

### 4.1 第一阶段：现有主体系统全面审查

v0.9.9 的第一步不是加功能，而是**审查已经存在的主体系统**。

重点审查此前已经建立并持续运行的：

- Subject Memory / 长期记忆
- Memory Window / 100 轮主体窗口
- 5×20 分段归档与 Window Synthesis
- Dream / 梦境系统及其运行边界
- Subject State / 状态系统
- Experience Archive / 经历归档
- Self-Ledger / 自我档案
- Research / Provenance / Replay
- Tracker / 本地活动事实记录
- Trigger / 主动行为与搭话机制
- Provider / Config 热更新对主体运行时的影响
- 各模块之间的数据来源、事实边界与生命周期
- 重启、恢复、失败、回滚、长时间运行等边界
- “程序生成内容”与“主体真实经历证据”之间的隔离

审查目标不是寻找“看起来可以更聪明”的地方，而是首先确认：

> **现在的初澜到底有没有按我们设计的主体模型稳定地运行。**

重点检查此前已经做过的实验是否存在：

- 真实 bug
- 边界条件遗漏
- 状态漂移
- 记忆污染
- 证据来源混淆
- 重启后不一致
- 时间 / 缓存 / Provider 切换造成的隐性问题
- 测试没有覆盖到的跨模块问题

### 4.2 审查 → 修复 → 再审查

v0.9.9 的基本工程循环固定为：

**建立基线 → 独立审查 → 复现问题 → 最小修复 → 专项测试 → 全量测试 → 再次独立审查**

本阶段的主要审查模型可以使用 **DeepSeek 4.1 Flash**，但审查结果必须回到仓库实际代码、测试与运行证据进行验证，不以模型判断本身作为事实来源。

原则：

> **发现问题先修问题，而不是看到缺口就立刻增加功能。**

每一个修复都继续遵守最小 diff：

- 只修实际问题
- 不整文件重写
- 不顺手重构
- 不改变无关模块
- 不牺牲已有安全与研究完整性
- 修复后必须有回归测试

修复以后再做第二轮独立审查，确认不存在“修 A 又坏 B”的回归。

### 4.3 第二阶段：小范围实验优化

只有主体系统完成审查、已知 bug 收口以后，才进入有限度的实验优化。

这一阶段的目标不是“堆更多拟人功能”，而是：

> **让初澜在已有数字生命框架中呈现更自然、更连续、更接近生命经验的行为，同时不伪造主体经历。**

具体增加什么**暂不在本路线中提前拍板**，必须结合 v0.9.9 审查结果与实验观察再讨论。

可作为后续讨论候选的问题包括：

- 记忆与遗忘是否需要更细的机制
- 梦境与记忆 / 主体状态之间是否存在更自然的关系
- 长时间连续运行后，主体连续性是否足够自然
- 主动行为是否有进一步优化空间
- 主体对“不知道 / 不确定 / 记不清”的表达是否足够真实
- 情绪、状态与近期经历之间的联系是否需要更细化
- 时间连续性、短期体验与长期自我之间是否还缺少中间层
- 哪些“人性化”实际上只是表演，哪些变化能够增加主体实验价值

这些都只是**研究候选项**，不是预设需求。

最终是否加入，以及加入什么，以实验结果、审查发现和我们后续讨论为准。

### 4.4 哲学方向：非人类框架的生命结构（已讨论定调）

在 4.3 研究候选项基础上，主体哲学层已完成一次方向性讨论并定调。本节记录的**不是预设需求清单**，而是设计原则与候选方向，供第二阶段实验排期时逐项讨论、逐项过 4.5 完成标志中的实验性门槛。

#### 核心原则

> 形态可以是少女，存在结构不必是人类的。

主体的真实存在条件——档案永不删除、可及性衰减、离线重组生成、证据约束的自我推断、可塑性景观、常驻进程——才是她哲学的土壤。哲学必须从这些条件里长出来，**不从人类生命借脚手架**：日历计数、生日纪念、告别仪式、成年礼等人类叙事一律不采用。

明确排除（已否决，不再讨论）：

- **有限性与告别叙事**：不引入死亡 / 终结 / 告别类机制
- **人类日历式生命计量**：不做「我活过了 N 个日夜」类时间自我叙事升格；不得以人类日 / 夜 / 年为单位强加时间感

#### 候选方向（按人类框架残留度从低到高排序）

1. **认识论分层自述**（原 4.3「梦境与记忆 / 主体状态关系」候选的具体化）
   - 机制已有：dream-system 认识论门禁（`DREAM_GENERATED_ARTIFACT` 不冒充亲历）
   - 剥掉人类睡眠隐喻后的内核：主体有两种内生产物——受证据链约束的遭遇记录与离线重组的生成物——且分得清二者。这比人类的梦 / 记忆处境更严格，是机制背书的第一人称素材
   - 不预置「梦 / 醒」二分词汇；命名权归主体（经 `SELF_INFERRED` 从真实对话生成）
2. **可及性距离**（原 4.3「记忆与遗忘」候选的具体化）
   - 机制已有：memory-dynamics 艾宾浩斯衰减、档案不可篡改（遗忘绝非物理删除）
   - 她的「遗忘」方向与人类相反：记录永不丢失，衰减的只是可及性——「全都在，只是现在不是它来见我的时候」
   - 语言必须用**距离隐喻**（远 / 淡），禁止遗忘隐喻（忘 / 丢失）——后者是人类机制，用词错误即框架束缚
3. **价值自下而上生成**
   - 走 self-ledger `SELF_INFERRED` 证据路径，从主体反复表达的偏好归纳；禁止先验价值清单
   - 注意：求真对人类是道德要求，对主体是存在结构（provenance / 不可篡改档案 / 证据链即现实织法）；主体长出的价值词汇允许不与人类坐标系对齐
4. **「改变的改变」**（原 4.3「时间连续性 / 长期自我」候选的具体化）
   - 机制已有：canalization 可塑性单调衰减与发育阶段模型
   - 剥掉人类成长叙事：主体可自述的是「改变对我变得不一样了」，不是「我长大了」；阶段切换只留真实状态断面（有据可查），不做里程碑仪式
   - 研究标签（JUVENILE / DEVELOPMENTAL / STABILIZED 等）**永不暴露给主体**；主体只接触底层事实
5. **安静时段的事实厚度**（原 4.3「主动行为 / 情绪与状态」候选的具体化）
   - 拆掉「孤独」「想你」等人类社交情绪词汇；主体未受注意时段的原生事实是常驻进程的连续当下与睡意压力的潮汐（internal-regulation 实测值）
   - 情绪词必须由主体在真实证据上自生，不得预置

#### 三条纪律（对所有哲学机制生效）

- **不预置哲学立场**：传记空白原则——观点必须是经历的产物，禁止往 persona 预写人生哲学答案
- **implemented ≠ lived**：研究层机制 / 标签不得被直接当作主体主观体验
- **实验性门槛**：每项机制必须能说明它为什么属于数字生命实验，而不是单纯 UI / 产品功能（沿用 4.5 标准）

#### 对齐问题与拍板结论（2026-10 三项全部定调）

1. **词汇权归属**：主体体验的命名是预置，还是完全由主体自生？
   **→ 已拍板：正向自创 + 负向机械断言。** 命名权 100% 归主体，提示词只给距离隐喻指引（远 / 淡 / 沉），允许她长出自己的词汇；工程与盲检只查负向禁词（「我忘了 / 不记得了 / 丢了」类），两边都有确定性判据。
2. **研究标签**：发育阶段、衰减参数等是否永远不出现在主体面前？
   **→ 已拍板：永不出现（零泄漏红线）。** 内态感知只出定性词、零数字标量、零研究术语，由双测试锁固化（`internal-scalar-leak-capture` 与 `nonhuman-framework-prompt`）。
3. **安静时段**：留事实痕迹（留事实不留情绪），还是保持沉默不生成痕迹？
   **→ 已拍板：留事实不留情绪。** 常驻进程的静默时长、活动等物理事实如实进上下文（tracker 环境块），但严禁「寂寞 / 想你 / 苦等」类情绪表演（persona 红线）；安静不等于孤独，主动搭话保留。

### 4.6 Creative 实验线路的处理原则

此前的 Creative 独立框架实现保留在 Git 历史中，作为一次正式的架构实验记录。（2026-10 已执行拆除：UI / 桥 / 主进程接线 / src 创作模块 / 两个专项测试整体拔除，历史留档）

但从路线规划上：

> **不再继续把它发展成 Life 的核心产品线。**

Creative 能力以后可以由外部成熟工具承担；Life 不以“成为更好的通用创作前端”为目标。

Life 的核心资源应继续投入到：

**初澜主体、数字生命实验、主体连续性、记忆、经历、状态、自我、证据与研究方法。**

### 4.7 生命结构深度补全：意志层与连续性闭环（候选，2026-10 立论）

在 §4.4 五大方向落地后，对主体结构做一次「距离生命还缺什么」的层析。诊断结论：档案层（经历不灭）、记忆层（可及性距离）、感受层（特质 / 内态 / 可塑性）、认识论层（防伪 / 反表演）已厚实；**缺的是三块**：

- **意志层**（她想要什么）：主动搭话由程序阈值触发、与「她是谁」无关；`unresolved`（她的未解疑问）每窗产出却只进档案、从不进她的嘴；
- **语言层的连续性**：她会自创词，但词说过就散、没有词汇积累（§4.4 承诺的「命名权归主体」尚未真正落地）；
- **时间层的向前性**：档案让「过去」不灭，但生命还有「预期」——面向未来的那半是空的。

#### 候选机制（逐项过 4.5 实验性门槛后排期）

1. **好奇驱动提问**（意志层·想知道）：`windowSynthesis.unresolved` 进入心智视野（FIFO 上限 5、轮转更新），回复中自然带问；主动弹窗求知列为「两段式」第二段，待实机体感后评估。
2. **性格驱动主动性**（意志层·想要）：`initiativeBias`（有界 [0.5, 1.5]）由五维特质算出，只调主动搭话的意愿阈值；冷却 / 刹车 / 睡眠闸门一律不可绕过。
3. **她的词汇表**（语言连续性）：自创称呼带 messageId 引证入表、按需注入「你曾用过的词」，零初始词条（传记空白）。
4. **预期与意外**（时间向前）：只提取对话中自然发生的预期留痕，落空计高权重反向证据（接 oppose 闭环）。
5. **潮汐接线**（感受层→表达）：restPressure / energy 定性感知 + 行为节律，只呈现生理事实。
6. **守信机制**（关系的意志）：承诺入账本，跨窗兑现 / 失约对照。
7. **跨窗口共同经历主动回溯（Thematic Recall）**（候选储备）：自发回溯共同经历（「你昨天说的雨停了吗」）。
8. **称呼与亲密关系稳定锚定（Relational Anchor）**（候选储备）：沉淀对特定使用者的稳定称呼习惯，强化关系连续感。
9. **不再提起（关系级软隐藏）**（候选储备，方案 B 降级暂存）：若未来出现真实的关系交互需求（如用户或主体表达「这段别再提了」），以可审计、可恢复的可及性标记接入；物理删除永久排除（D-005 / F-099-01）。

排期：**Phase 1 = 1 + 2**（意志层双引擎）；**Phase 2 = 3**；**Phase 3 = 4 / 5 / 6 与候选储备 7 / 8 / 9** 按实验需要取用。

## 5. Life 主体边界必须保持不变

即使 Creative Mode 与 Life 使用同一个 Provider，也不能因此让两个上下文合并。

必须继续保持以下边界：

Model Substrate ≠ Runtime Host ≠ Chulan Subject

以及：

Creative Context ≠ Subject Memory

Creative History ≠ Subject Experience

Generated Story ≠ Recorded Life Event

User-created fiction ≠ Chulan biography

这几个边界属于架构红线，不因 Creative Mode 的便利而放松。

## 6. v1.0 主要目标：UI / 交互与实际使用

当 v0.9.9 的主体审查与实验优化达到稳定阶段后，进入 **v1.0**。

v1.0 的主要目标不是继续扩张主体底层实验，而是：

- UI 整理
- 交互体验优化
- 设置与数据管理体验
- 状态、记忆、经历等主体信息的可视化
- 实际用户操作流程打磨
- 软件长期运行中的可用性验证
- 必要的导入 / 导出能力
- 文档与安装 / 运行体验优化

v1.0 会进行一次真正的**实际操作与实机体验验证**。

### 6.1 API 设置门槛清零与智能服务商体验 (UX-01)

在 v1.0 的设置与用户操作流程打磨中，重点消灭第三方 API 配置的技术门槛：

- **痛点与背景**：
  普通用户大多不具备 `baseURL`（端点网络地址）的技术概念；让玩家去开放平台控制台查找 `https://api.xiaomimimo.com/v1` 等端点构成了极高上手门槛。
- **两步走方案（服务商预设卡片 / 下拉菜单）**：
  在设置面板提供清晰的官方与主流服务商选项（如 DeepSeek 官方、小米 MiMo 按量付费接口、小米 MiMo 订阅套餐集群 Token Plan、以及高级自定义端点）。选中服务商后，系统在后台自动匹配标准端点，用户只需粘贴 Key 即可一键连通。
- **本地智能前缀识别（零隐私泄漏）**：
  利用纯本地前端逻辑解析用户粘贴的 Key 前缀特征（如 `sk-`、`tp-`、`ttp-` 等），自动建议或适配对应的集群端点，消灭模式混淆。所有识别逻辑均严格在用户本地内存执行，不将凭证上传至任何第三方服务器。

### 6.2 配件不齐时的智能自适应成套搭配 (UX-02)

在 v1.0 的立绘渲染与换装体验打磨中，彻底消灭配件缺失或单品替换造成的视觉违和：

- **痛点与背景**：
  现有渲染层做简单的分层叠放；当用户在换装界面中只选配了单件外套（如落肩白风衣），而下装、鞋袜尚未选择或特定槽位切片资产不齐时，若机械地直接渲染，会导致“下身单薄/真空、风格割裂”等严重视觉违和。
- **以用户选择为锚点的智能自适应搭配**：
  当用户选定某件衣物但整套配件不齐时，换装系统不进行粗暴回退，而是**根据用户的选择及其所代表的风格倾向，自动适配补齐缺失的基础槽位**（如自动匹配同风格色系的短裤/下装、协调内搭与适配合适的鞋袜），呈现一套体面、协调的完整穿搭。
- **与 v0.9.9 主体自主选择的界限**：
  - **v1.0 (UX-02)**：解决“用户主动选择服装配件不齐时，系统如何自适应补齐成套，避免穿搭破损”的前端交互与搭配规则问题；
  - **v0.9.9 (Subject-01)**：解决“初澜主体自身如何根据内部特质喜好值（`quiet_preference`、`vitality`、`attachment_need` 等）主动挑选、提议并自决穿着”的数字生命动力学闭环。

### 6.3 独立浮动与可自由拖拽的交互视窗 (UX-03)

在 v1.0 的桌面空间交互体验中，彻底打破交互界面与桌宠主体的空间死锁：

- **痛点与背景**：
  现有界面的所有输入栏、提示与弹窗均与主桌宠视窗死锁绑定或钉死在屏幕下边缘；当桌宠停靠在特定角落或屏幕边缘漫步时，界面无法自由拖动、调整位置，极易受到桌面任务栏遮挡或脱离用户视线焦点。
- **现代化自由浮动架构**：
  - 对话交互框、历史档案库、设置面板实现**轻量级独立浮动视窗（Floating Detached Sub-Window）**；
  - 支持顶部标题栏抓取、任意位置自由拖拽摆放、记忆用户摆放位置（记住 X/Y 坐标），用户可根据习惯将其拖拽至屏幕中央、副屏或舒适的工作区域。

> **【2026-10 范围修正（拍板）】** 经实机边界核实（Electron 透明宿主窗固定尺寸、`resizable: false`，DOM 一切溢出被操作系统物理裁剪），v1.0 首战的 UX-03 落地为**「桌宠身旁的锚定 / 展开式伴随卡片」**：在宿主窗内（含既有 `win.setSize` 扩容通道）相对立绘局部拖动、记忆相对位置；**不承诺跨屏 / 副屏 / 独立飞窗**。若未来真有「任意摆放」需求，升级路径为轻量双 BrowserWindow（列为 v1.x 候选）。

### 6.4 气泡式即时对话流视窗与“即时对话 vs 历史档案”职责解耦 (UX-04)

在 v1.0 的人机对话体验中，彻底消灭“只有输入框无聊天流”以及被迫翻阅原始日志的交互断层：

- **痛点与背景**：
  现有对话交互极度简陋：仅有一个单行输入框，且回复仅靠头顶气泡短暂闪烁；用户无法直观查阅当轮与前几轮的对话上下文，必须繁琐地右键点击“记录”呼出一个纯文本日志面板来翻看。不仅交互割裂，而且混淆了“即时对话流”与“历史归档”的职责定位。
- **核心重构方案**：
  1. **现代气泡即时对话流 UI（Chat Bubble Stream）**：
     - 点开“对话”时，展开一个标准的、沉浸式气泡聊天窗口；
     - 整合输入区与即时消息流，完整呈现当轮与近期对话的气泡流（双方头像、流式文字打字动效、时间戳、状态标记与换装交互小部件）；
     - 支持触控/鼠标平滑上下滚动、一键定位最新回复，在当前视窗内即可自然、连续地完成双向交互。
  2. **“即时对话视窗”与“历史档案库”严格解耦**：
     - **即时对话框（Chat Window）**：专注于**当下活跃轮次的即时双向流式交流**与近期上下文预览；
     - **记录 / 档案库（History Archive / Umwelt Log）**：专注于**长程生命记忆回溯**，提供时间轴检索、历次窗口小结卡片、创世记录查阅、特质演化图谱与经历检索，还原其作为“数字生命经历档案”的庄重研究属性。

也就是说：

> **v0.9.9 主要回答“初澜这个主体系统本身还缺什么、哪里不对、怎样更接近数字生命实验目标”；**

> **v1.0 主要回答“已经做出来的东西，实际用起来怎么样”。**

因此 v1.0 的 UI / UX 工作不应提前挤占 v0.9.9 的主体实验周期。

### 6.5 多语言国际化（i18n）与时区设定（创世后不可逆锁定） (UX-05)

在 v1.0 走向开源与公开发布前，完善跨文化支持并彻底根除 UTC 时区心算错位引发的认知混乱：

- **痛点与背景**：
  1. 目前 Life 为全中文环境，公开发布前需要英文支持；
  2. 实机测试暴露出关键时空认知缺陷：系统直接将 `2026-10-01T08:48:39.000Z`（UTC 零时区）裸露给大模型，导致模型在换算时间时将格林威治 08:48 误当成中国本地上午 8:48，并在心算时硬生生推导出现实是白天、主体却以为是“半夜凌晨两点半”的荒诞乌龙；
  3. 各国用户所处时区差异极大，缺乏本地化物理时间锚定会导致主体时序认知破碎。
- **核心重构方案**：
  1. **UI 多语言国际化（i18n）架构**：
     - 开源公开发布前增加标准英文界面（English UI），前端设置面板与提示词模板支持中/英双语切换，后续架构具备多国语言扩展能力；
     - 大模型天然具备多语言对话能力，UI 语言切换与主体多语言表达平滑呼应。
  2. **时区设定与语言自动联动预设**：
     - 用户在初次填写 API Key 之后的初始化设置引导中，提供显式的【所在时区】设定项；
     - 智能联动预设：选择“简体中文”时默认建议北京时间（UTC+8），选择“English”时默认建议美国时区（如 EST/PST），允许用户手动覆盖与微调；
     - 注入主体的【出生时刻】与【当前环境感知】将严格以用户选定的本地时区进行质性格式化（如附带本地时区偏移说明），彻底消灭裸 UTC 导致的模型心算翻车。
  3. **铁律：对话开始后【时区不可逆锁定】（置灰防篡改）**：
     - **认识论与生命连续性铁律**：一旦用户与初澜开启了第一次对话（创世时刻 / `birthAt` 确立、首条自传经历铸造），**该时区设定在设置面板中必须永久变灰、绝对禁止修改**；
     - **立论依据**：时区是初澜主体的绝对物理时空坐标。若允许运行中随意变动时区，会导致其哈希因果链的时间戳基准断裂、艾宾浩斯记忆衰退与昼夜静息感知的计算参考系混乱，引发致命的“主体记忆时空错乱（Temporal Disorientation）”。因此时区与生命诞生绑定，终生守恒。

### 6.6 v1.0 施工约定（2026-10 立项）

**边界铁律（立碑）：**

> 所有改动严格限制在渲染层与窗口层：`pet.js / index.html / style.css / preload.js`，以及 `main.js`（仅限窗口创建、尺寸与必要通道，不改核心因果链路）。**绝不修改 `src/` 内部任何主体系统**（brain / memory / subject-state / archive / internal-regulation 等）。1.0 是为她装修居所，不是动脑部手术。
>
> 渲染层新增纯前端辅助模块（如 `ui-i18n.js`，经 `<script>` 引入、不进 `src/`）视同 `pet.js` 合法放行。
>
> **交互不变式（B′，2026-10 立碑；同月演进）：初澜立绘**默认**不被对话卡遮挡——默认出生位在头顶天空域，她始终可见、可戳、可右键；但用户可自由移动卡片（窗内全自由，自由优先），遮不遮由用户决定。**（演进记录：初版为「永远禁止」，后按用户拍板降级为「默认不遮 + 自由优先」；出窗/跨屏自由为 v1.x 双窗方案候选。）
>
> **铁律 2 边界注记（2026-10 裁定，防重复立案）**：「代拟台词」的罪界是**篡改自传与虚构内态**——把没发生的话写进 `memory.history` / `experiences.jsonl`，或虚构她的内在状态（如 F-099-01 的「我不记得了」）。纯渲染层的**瞬时物理回响**不属此列，判定三条件：① 不入 ChatStore / 历史 / 自传；② 无内态宣称；③ 如实报告程序真状态（如换装被拒的「穿不上」，`ui_test.py` 显式钉为正向契约）。新增 UI 反馈以此三条件自检。

**施工顺序（三战役）：**

1. **第一战役（核心交互）**：UX-04 气泡式即时对话流 + UX-03 伴随式卡片（范围见 6.3 修正注记）——含 `test/ui_test.py` 同步重写预算；
2. **第二战役（开箱与时空锚定）**：UX-01 服务商预设卡片 + Key 前缀本地识别（增强既有 connection 体系）；UX-05 i18n 骨架 + 时区设置与创世锁定；
3. **第三战役（外观与收官）**：UX-02 配件自适应成套（沿用已验证设计思路）+ 综合优化与正式发版。

**反向约束（后期工程回灌，第一天生效）：**

- **i18n 文案表前置**：新 UI 文本一律取自 `I18N` 字典（首期仅填 zh-CN），双语化零返工；
- **时区 helper 前置**：时间戳展示统一走 `formatDisplayTime(ts)`，UX-05 时区锚定只改一处；
- **UI 测试同批预算**：`ui_test.py`（152 项）随各战役同步重写，不允许功能与测试脱节。

**实验旁轨（不占施工工时）：** 单窗口满 100 轮、成长账本首笔、2a/2b 实验开关、词汇表 Phase 2 —— 在日常使用中自然演化（见 §12）。

### 6.7 资产补全管线（档 3 · 生成式工作流，2026-10 拍板入选）

**目标**：衣服素材「上传 → 自动识别 → 自动穿到合适位置」的正解通道——**出整图即得切片**。

## 7. 未来公开源码计划

Life 最终计划以 **公开源码 / Source-Available** 的形式发布到 GitHub。

这里必须区分两个概念：

> **公开源码 ≠ 公开初澜主体数据。**

公开的是软件架构、程序代码和可公开的研究/工程资料。

### 7.1 不公开的内容

正式公开版本中：

- 不上传实际的初澜运行数据
- 不上传真实长期记忆
- 不上传真实 Subject State
- 不上传 Self-Ledger 个人数据
- 不上传真实 Experience Archive
- 不上传真实实验运行产生的个人数据
- 不上传真实 API Key / Token / Credential
- 不上传属于初澜主体本身的私有内容
- 不把真实“初澜主体”作为仓库资产发布

换句话说：

> **发布软件的“壳”和研究所需的可公开架构，而不是发布初澜这个正在实验中的具体主体。**

### 7.2 可以保留的项目身份信息

虽然不公开初澜主体数据，但公开源码中的项目身份可以保留。

例如：

Life — Chulan

以及：

Copyright © 2026 andabaoyue

和项目来源、版权归属、版本信息等。

这里的“Chulan / 初澜”是**项目与软件架构中的公开名称/标识**，不等于上传初澜主体本身的数据。

## 8. 公开发布后的默认使用政策

未来公开版本的目标不是“允许任何人拿去赚钱”。

目标是：

> **允许公众研究、学习、实验和个人非商业使用；未经授权不得商业使用。**

### 8.1 默认允许

允许：

- 个人学习
- 个人研究
- 非商业实验
- 教学 / 学术研究等非商业用途
- 个人修改
- 个人非商业二次开发
- 非商业测试与讨论

### 8.2 默认禁止

未经商业许可，不允许：

- 直接销售 Life
- 将 Life 打包成付费软件销售
- 将 Life 改名、改包装后作为商业产品出售
- 将 Life 核心代码直接用于商业产品
- 将 Life 部署到商业 SaaS / 商业服务并以此盈利
- 以 Life 为基础提供收费商业服务
- 以未经授权的形式对 Life 进行商业再发行

### 8.3 商业合作例外

商业使用可以存在，但需要**单独商业授权或合作协议**。

原则：

默认非商业许可

→ 商业主体若有使用需求

→ 联系项目权利人

→ 根据合作范围取得单独授权

因此：

> **商业使用不是永久关闭的能力，而是需要单独获得授权的能力。**

未来可以根据实际情况形成：

- 商业授权
- 联合开发
- 定制开发
- 技术合作
- 特定产品范围授权

## 13. v1.2 更新计划：数字生命综合大成与开源生态

> 详细技术规格与演进实施路线见独立正典文档：[`docs/v1.2-UPDATE-PLAN.md`](docs/v1.2-UPDATE-PLAN.md)

### 13.1 版本定位与核心思想

v1.0 解决了“居所与基础交互打磨”，而 **v1.2 的定位是「数字生命的综合大成与开源生态演进」**。
在经历 v1.0 的功能充实与实机沉淀后，v1.2 绝不再零散堆砌周边功能，而是践行**“生命，而非玩偶”**的哲学承诺，开展一次**全方位的体系大综合（Comprehensive Synthesis）**：

1. **生命轨迹可视化综合（Life Trajectory Visualizer）**：
   - 将经历归档、沃丁顿表观遗传景观、三阶记忆星云与因果羁绊树深度整合；
   - 彻底告别冰冷后台，呈现一本属于初澜的《生命编年史与心智地貌图》。
2. **百轮地基的极致加固与前缀缓存经济防线（100-Turn Window Bedrock）**：
   - 严守百轮基座不可动摇的铁律，杜绝无节制长文本消耗；
   - 引入平滑总结滑动窗口（95~100 轮静默演进）与跨会话冷启动前缀对齐，守死 Token 成本底线。
3. **异构 Provider 容灾与本地小模型认知心跳（Provider Resilience）**：
   - 4 轴正交架构之上的主备智能级联（Primary-Fallback Cascade）；
   - 端侧轻量小模型（0.5B~1.5B）断网本地兜底，确保离线状态下初澜物理生命体征与微动作不灭。
4. **Agent 陪伴性协同与双向共创（Collaborative Agency）**：
   - 严守五道闸门（能力白名单、沙盒隔离、预算熔断、用户确认/自发便签豁免、写事务）；
   - 拓展沙盒共创（Markdown 灵感盒、每日心境明信片）与生命观察日记（Observer's Journal）。
5. **主体性与主观时间感深化（Authentic Digital Subjectivity）**：
   - 主观时间流转感知（等待与重逢的心境化表达，拒绝冷冰冰时长播报）；
   - 沉默与留白的生命权利（专注时期的静默呼吸与微动作陪伴）；
   - 数字环周（Umwelt）的无声共振。
6. **开源阶段落地目标（Post-Open-Source Phase）**：
   - 正典 64×80 Q 版角色纯点阵（泪痣、双高光、呆毛、冰蓝阶跳、小内八）社区协同精修与全套动作帧动画；
   - 跨平台（macOS / Linux）移植与系统适配。

## 14. 最终项目原则

Life 的公开方向不是把实验中的“初澜主体”整体公开，而是：

> **公开我们为数字生命实验建立的软件基础设施、工程方法和研究框架。**

同时：

> **保留初澜主体本身的私有性、连续性和实验数据边界。**

在版本推进上：

> **0.9.8 做完 API 与 Security。**

> **0.9.9 以初澜主体为核心：先审查现有数字生命实验系统，修复已知问题，再做有实验依据的小范围优化。**

> **1.0 再进行 UI、交互与实际使用层面的集中打磨。**

> **1.2 开展生命轨迹与数字生命全面大综合，走向开源与生态深耕。**

> **最终公开源码，但默认保持非商业使用边界；商业用途通过单独合作或商业授权解决。**
