## 0. 为什么需要这份清单

2026-10-18 夜到 10-19 晨的实测事故：她整夜零开口。事后靠三份数据交叉才定出根因：

| 证据 | 读数 | 说明 |
| :-- | :-- | :-- |
| `experiment-telemetry.jsonl` | 20:40:13 有 `perception_attach`、**无** `llm_call` | 她进了 `brain.ask`，请求没走完 |
| `memory.json` | 最后一条 assistant 停在 19:47:48 | 没有新回复落盘（`rollback` 生效） |
| Windows 电源日志 | 22:30:43 进 Modern Standby，次晨 06:10:41 才退出 | 中间只在 02:35 / 03:29 / 05:09 / 05:39 / 05:43 / 05:45 有短缝隙 |

根因不是防骚扰铁律（`spokenDuringIdle` 全程 `false` —— 她一个字都没说出口，那道刹车根本没参与），
而是 `checkAndPushProactive()` 在「已派发提案」这条分支上**不安排下一次 tick**，
整条链的存续完全押在渲染端回执上；回执被休眠冻住，调度就永久停摆。

**所以这份清单的验收标准不是「她说话了吗」**，而是：
**下一次该评估的时候，评估有没有发生。**

## 1. 观测手段（先准备好，四项验证共用）

实时看审计流（PowerShell，另开一个窗口，让它一直开着）：

```powershell
Get-Content "$env:APPDATA\Life\agent-audit.jsonl" -Wait -Tail 20
```

判读口径（修复后新增了 `proactive-offer` 这一类记录）：

| 审计里出现的形态 | 含义 |
| :-- | :-- |
| `channel:"proactive-offer", outcome:"dispatched"` | 主进程确实出了提案 |
| 其后有 `channel:"proactive-declined"` | 被渲染端礼貌闸门拒了（用户正在对话/气泡开着），**正常** |
| 其后既无 `declined` 也无新的 chat 记录 | **回执丢了** —— 90 秒后应看到第二条 `proactive-offer` |
| 有 `proactive-offer`，`llm_call` 遥测却没有新增 | 提案进了 brain 但请求失败（网络/配额） |

补充：`%APPDATA%\Life\experiment-telemetry.jsonl` 每行只追加，可用于核对「有没有真的调模型」；
`%APPDATA%\Life\internal-regulation.json` 的 `history` 数组可用于核对唤醒时刻（每条带毫秒时间戳）。

## 2. 验证项

### V1：Modern Standby 唤醒后自愈（本轮主目标）

**为什么单独验它**：`powerMonitor.on('resume')` 只在 `main.js` 的 `whenReady` 里注册一次，
而 Windows 的 Modern Standby 与经典 S3 行为不同，Electron 不保证每次退出待机都派发 `resume`。

**步骤**

1. 启动 Life，确认托盘图标在、窗口正常。
2. 让它静默挂机（不戳、不拖、不对话）**至少 25 分钟** —— 她的 `idleNeed` 是 20 分钟
   （`attachment_need: 174` / `social_initiative: 86` / `quiet_preference: -44` 算出 bias = 1.5，
   30 ÷ 1.5 = 20 分钟；这是实测值，不是默认的 30 分钟）。
3. 合盖或手动进入睡眠（开始菜单 → 电源 → 睡眠）。**保持 5 分钟以上**。
4. 唤醒，**不要碰桌宠、不要发消息、不要开对话窗**。
5. 观察审计流。

**通过条件**

- 唤醒后 **45 秒内**（`COOLDOWN_MS`）应能看到调度恢复的证据；
- 这个证据分两种，任一即可：
  - 若唤醒时静默已过 20 分钟门槛 → 45 秒内出现一条 `proactive-offer`；
  - 若还没到门槛 → 45 秒那次评估返回 `null` 并照常重排，
    之后静默到达 20 分钟时**照常**出提案（而不是像修复前那样，要等用户碰一下才恢复）。

> ⚠️ 别把「45 秒后没说话」当失败：`resume` 那条只负责**把调度叫醒**，
> 说不说仍由 `evaluate()` 按静默时长、冷却、睡眠闸门独立判定。

**失败判据**

- 唤醒后静默继续超过 30 分钟仍**完全没有任何** `proactive-offer`，
  且用户轻戳一下后立刻恢复 → 说明 `resume` 事件没派发、兜底也没接上，需回头查。

### V2：回执丢失后的 90 秒自愈

**为什么单独验它**：这是 D1 的直接行为变化，修复前一次丢回执就是永久沉默。

**步骤**（不必等休眠，可人为制造）

1. 挂机到出提案（观察 V1 第 2 步的时机即可）。
2. 在提案发出的**那 90 秒内**，让渲染端无法回执 —— 最简单的做法是
   在桌宠窗口的 DevTools 里断开 IPC 监听，或直接把聊天/桌宠窗口最小化到不可见（视版本而定）。
3. 盯住审计流 3 分钟。

**通过条件**

- 若回执确实丢了：约 90 秒后出现**第二条** `proactive-offer`（`OFFER_RETRY_MS = TTL + 冷却`）。
- 若回执没丢：出现 `proactive-declined` 或她真的说了话，也是通过（说明闸门正常工作）。

**失败判据**

- 90 秒后既无第二条 offer、也无 declined、也无发言 → 自愈重排没生效。

### V3：冷启动无 Key → 填 Key 后自动恢复

**为什么单独验它**：修复前 `!brain.ready` 那条分支直接 `return`，调度器当场停摆；
用户后来填好 Key 也**不会**自己回来（要等下一次互动）。

**步骤**

1. 把配置里的 Key 清空（右键 → 设置，或直接改 `%APPDATA%\Life\life-config.json` 后重启）。
2. 启动 Life —— 此时 `brain.ready === false`，调度器应进入 60 秒重试循环。
3. **什么都不点**，让它挂 5 分钟（确认它没有崩、窗口正常）。
4. 右键 → 设置 → 填入 API Key → 确定。
5. **仍然不碰桌宠、不发消息**，盯审计流 3 分钟。

**通过条件**

- 填完 Key 后 **45~60 秒内**应能看到评估恢复的证据（任一即可）：
  - 出现 `proactive-offer`（若此时静默已过门槛）；
  - 或静默继续累积、到达门槛时**自动**出提案，无需任何用户互动。

> 代码事实（避免误判）：`config-set-key` 成功分支里写的是
> `scheduleProactiveCheck(COOLDOWN_MS)`，即 45 秒。
> **为什么不是基准（30 分钟）**：`scheduleProactiveCheck` 会先清掉已有定时器，
> 若这里用基准，就会把「AI 未就绪时正在排队的 60 秒重试」直接覆盖成 30 分钟等待 ——
> 那等于修复本身被自己关掉。所以这一行必须取「短延迟」这一侧的常量。
> 说不说仍由 `evaluate()` 独立判定：静默不够久就返回 null 并照常重排。

**失败判据**

- 填完 Key 后 5 分钟仍无任何 offer，且必须戳一下才出现 → 说明重排没生效或 60 秒循环没在跑。

### V4：D-25 好奇破冰两条入口一致

**为什么单独验它**：修复前后台 tick 传了 `curiosityPending`，而 `proactive-check` IPC 漏传，
同一个引擎在两条入口上给出不同答案 —— 好奇破冰只在后台那一半世界里存在。

**步骤**

1. 确认 `%APPDATA%\Life\memory.json` 里 `curiosityQueue` 有 `asked` 不为 `true` 的项
   （正常使用会自然积累；若无，可先聊满一个窗口让它关窗产出）。
2. 挂机到 30 分钟以上（`curiosityIdleMs` 默认 30 分钟）。
3. 分别在两种时机观察产出的 `selfIntent.kind`：
   - **后台路径**：静默到点，审计里的 `proactive-offer` 应带 `selfIntentKind:"curiosityAsk"`（若未被更高优先级覆盖）；
   - **渲染端路径**：在渲染端触发一次 `proactive-check`（DevTools 或连戳 5 下），同一个时间点应给出**同样**的 kind。

**通过条件**

- 两条入口在同一状态下给出**相同的** `offerKind` 与 `selfIntentKind`。
- 注意排序：`wantToLeaveSomething`（静默 ≥120 分钟）优先级最高，
  那时会盖掉 `curiosityAsk` —— 这是**设计如此**，不算失败。

**失败判据**

- 后台 tick 出 `curiosityAsk`，而同一时刻渲染端 `proactive-check` 出 `idle` 且无 `selfIntent`
  （或反之）→ 两条入口仍未对齐。

## 3. 已知边界（不要误判为缺陷）

| 现象 | 定性 |
| :-- | :-- |
| 唤醒后**立刻**说话 | 不应发生 —— 设计是隔一个冷却（45 秒）再复查。若立刻弹，说明有别的路径在绕过冷却，需查 |
| 她整夜只在几个时刻动一下 | Modern Standby 期间进程被冻结，定时器不走表，这是 OS 行为不是缺陷 |
| `resume` 事件在某些平台/机型不派发 | 已知风险；此时仍有 V2 的 90 秒兜底在线，不会退回「永久沉默」形态 |
| 回执丢失后 90 秒内重复出提案 | 正常 —— 提案未 commit 就不消耗冷却与 `spokenDuringIdle`，重排只是再产出一份本地提案，**不产生 API 调用** |
| 审计里 `proactive-offer` 一天很多条 | 需留意但不是缺陷：它只记「主进程想说话」，真正说出口才由 `chat-send` 记账 |

## 4. 若验证失败，先查这三处

1. `main.js` 的 `checkAndPushProactive` 里三条出口是否都还有 `scheduleProactiveCheck`
   （`node test/proactive-scheduler.test.js` 的 ⑪ 项就是钉这个的：`hits >= 3`）。
2. `whenReady` 里的 `powerMonitor.on('resume', ...)` 是否还在（同文件 ⑮ 项）。
3. `ipcGuard.handle('config-set-key', ...)` 成功分支末尾是否还有重排（同文件 ⑭ 项）。

这三条一旦被「顺手改回去」，`test/proactive-scheduler.test.js` 会直接红 —— 先跑它，再谈实机。

## 5. 修复前后对照（一句话版）

| | 修复前 | 修复后 |
| :-- | :-- | :-- |
| 丢一次回执 | 永久沉默，直到用户互动 | 90 秒后自愈 |
| 冷启动无 Key | 调度器停摆，填 Key 也不回来 | 60 秒重试循环 + 填 Key 显式重排 |
| 系统唤醒 | 无人对齐，靠偶发事件撞醒 | `resume` 后隔冷却复查 |
| 好奇破冰 | 只有后台 tick 半边生效 | 两条入口共用 `evaluateTriggerWithCuriosity()` |
| 事后排查 | 只能靠遥测 + 电源日志倒推 | 审计里直接有 `proactive-offer` 留痕 |
