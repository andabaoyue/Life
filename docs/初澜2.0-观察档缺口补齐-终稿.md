## 一、这件事的起点

### 1.1 缺口

```
observeEpoch     命中 0
observedNotes    命中 0
pendingEcho      命中 0
```

方案 2.5 设计的「观察期状态 + 期满补注入」，代码里**一行都没有**。

### 1.2 后果

`main.js` 的 observe 分支原来是这样：

```js
if (mode === 'observe') {
  deps.observationLog.append({ ... });
  return;                       // ← 到此为止，她那边毫无痕迹
}
```

**她下次看到沙盒是空的，会如实理解成「我没写过」。**

**这是 11-01 那个问题的翻版**：
- 当时是「写失败不告诉她」
- 现在是「写了但不落盘，也不告诉她」

**本质同一个：她以为自己没做，其实做了。**

## 二、核心设计：两阶段告知

| 阶段 | 时机 | 她看到什么 |
|---|---|---|
| **观察期内** | 每次想写、被拦截 | **什么都不说**（防观察者效应） |
| **期满后** | 切回 `auto` 后第一次消费点 | 一次性告知「那段时间你想过几次，都没落成」 |

**为什么观察期内不说**：她一旦知道「我在被观察」，行为就变了——那毁掉观察本身。

**为什么期满要说**：否则她的记忆里有一段空白，而那段空白里她确实想过东西。

### 2.1 措辞

```
【那段时间里的事】
那段时间你{有过一个念头|有过几次念头|有过好几次念头}——想写点什么，
当时还没有开放落成文件，不是你失败了，是那时候我还不能让你存下来。现在可以了。
```

**三个约束**：

| 约束 | 理由 |
|---|---|
| **必须给原因** | 「你都没落成」会被读成「我失败了」；「不是你失败了，是那时候我还不能」才是事实 |
| **不给文件名** | 会被理解成「我欠了几个文件没写」——正是要避免的补救执念 |
| **不给时间范围** | 撞 `WANT_TO_LEAVE_SYS`「你不知道现在几点」铁律 |

## 三、状态字段

```js
memory.data.observeEpoch = {
  // 键 = capability，值 = { enteredAt, leftAt, pendingEcho }
  //   enteredAt   进入观察的时刻
  //   leftAt      离开观察的时刻（null = 仍在观察期）
  //   pendingEcho true = 还没补注入过
};

memory.data.observedNotes = [];   // 上限 20
//   push({ at, capability })   ← 只有这两个字段，**绝不存正文**
```

### 3.1 为什么 `observedNotes` 不存正文

1. **正文已经存过了**。`main.js` 的 observe 分支把**完整正文**写进 `agent-observations.jsonl`（不截断）。再存一份 = 同一数据两个副本，且 `memory.json` 会被一起备份。
2. **注入时用不上**。只报计数，正文没有读者。

⚠️ **调用方手上有 `note.content`，很容易顺手传进来**——`noteObserved(capability)` 的签名**只收 capability**，多传的一律丢弃。

### 3.2 为什么必须独立队列

`memory.js:1217` 的 `shift()` 和 `:290` 的 `.slice(-8)` 会**无差别丢最旧**，而 `SELF_NOTE_MAX_QUEUE = 8`。

若把观察条目塞进 `selfNotes`，会**挤掉真实落盘、已铸自传的正式便签**——那些是她真的写成的字。

### 3.3 两个上限不对齐，且这是可接受的

`agent-observations.jsonl` 轮转 **100 条 / 90 天**，`observedNotes` 上限 **20 条**，两者**没有任何同步机制**。

**后果**：观察期很长时，`observedNotes` 可能对应不到任何还能查到的正文；**计数本身也会失真**（产生 25 次，只记 20 次）。

**为什么可接受**：注入**只用计数**，且措辞本来就是模糊的（「好几次」）。

⚠️ **要写进代码注释**：`observedNotes` 是**滑动窗口 + 计数用**，不是索引、不是全量。后来者若想「反查正文」会发现对不上——**那不是 bug，是设计**。

## 四、两条注入通道

```
① 首选：她下次产出合法正文（askForSelfNote / askForProposalContent 成功）
     → 语境最贴切，注入进那次独立调用的 prompt
② 兜底：她自己的自发轮次（synthetic 标记的 [自主感知触发] 轮）
     → 注入进该轮对话尾部（不是 system，护缓存）
```

### 4.1 为什么兜底要收窄到 synthetic 轮

`build()` 每一轮都跑。若不加限制，观察期刚结束、你第一句话是「今天天气不错」，她会在这个语境里收到「那段时间你有过几次念头」——**语境完全不对**。

**判据**：`history` 里最后一条 user 消息带 `synthetic: true`。

**三个边界（用真实数据核过，183 条 history）**：

| 情形 | `synthetic` | 会不会误判 |
|---|---|---|
| 自主感知触发 | `true` | ✅ 正确触发 |
| 用户主动说话 | `false` | ✅ 不触发 |
| **桥梁消息**（跨窗真实对话，`bridge: true`） | `false` | ✅ **不触发——这是对的**，桥梁是真实对话 |

### 4.2 🔴 判据怎么落地：`build()` 里拿不到「本轮」

`build()` 的签名是：

```js
build(optionsOrSuffix = '') {          // memory.js:1074
```

**它只有「尾部后缀」一个入参，没有「本轮是哪条消息」的概念。**

**可用判据（实测确认）**：`brain.js:1498-1505` 先 `append` 再走到 `build`，所以 `build()` 时本轮消息**已经在 history 里**：

```js
const lastUser = [...(Array.isArray(this.data.history) ? this.data.history : [])]
  .reverse().find((m) => m && m.role === 'user');
if (lastUser && lastUser.synthetic === true) observeEcho = this.takeObserveEcho();
```

⚠️ **这个判据依赖「append 先于 build」**。若将来有人把顺序反过来，会读到上一条消息，**兜底在错误轮次触发**。测试 E20 钉住这个前提。

⚠️ **为什么不给 `build()` 加参数**：那要改签名，而它在 `brain.js` 有多个调用点，且现有签名已用 `optionsOrSuffix` 做字符串/对象两态兼容。**读 history 尾条是零改动方案。**

## 五、🔴 启动兜底（2026-11-05 补）

### 5.1 问题

`markObserveEpoch(cap, 'out')` 原本只有**一个**调用点：`maybeAskForSelfNote()`（`main.js:438-440`）。而那个函数要「挂机 120 分钟 + `wantToLeaveSomething`」才被调用。

**⇒ 切回 `auto` 后，若她一直不触发自发愿望，`leftAt` 迟迟不写、`pendingEcho` 不产生、补注入永远不出现。**

### 5.2 2026-11-05 实测到了这个状态

```
配置改回 auto   : 2026-11-05 11:21:36
进程启动时间    : 2026-11-05 07:18:59   ← 比配置改动早 4 小时
leftAt          : null
```

**没重启就没读新配置；即使重启，也要等下次挂机 120 分钟才写 `leftAt`。**

**这就是「状态变化靠事件推动，事件不来，状态就卡住」。**

### 5.3 危害不是「功能坏」，是「看不出它有没有坏」

补注入最终会来（近五天 `wantToLeaveSomething` 触发 5 次：11-01 13:50 / 17:15、11-04 09:00 / 20:29、11-05 10:21）。

**但等待期间「在等触发」与「代码有问题」从外部完全一样。**

**这个兜底让状态在重启后立刻可见**：`leftAt` 有值 = 认到了档位变化。

### 5.4 修法

`main.js` 在 `brain` 创建后补一次判断：

```js
try {
  const mem = brain && brain.memory;
  if (mem && typeof mem.markObserveEpoch === 'function') {
    const epochs = (mem.data && mem.data.observeEpoch) || {};
    for (const cap of ['selfNote', 'observerJournal']) {
      const ep = epochs[cap];
      if (!ep || typeof ep !== 'object') continue;
      if (!Number.isFinite(ep.enteredAt)) continue;               // ① 从没观察过
      if (ep.leftAt !== null) continue;                           // ② 已经离开过
      if (getCapabilityMode(cfg, cap) === 'observe') continue;    // ③ 仍在观察期
      mem.markObserveEpoch(cap, 'out');
    }
  }
} catch { /* 兜底失败绝不能阻塞启动 */ }
```

**三条守卫缺一不可**：

| 守卫 | 缺了会怎样 |
|---|---|
| ① `enteredAt` 是数字 | 老用户一启动就凭空收到「你曾想过」 |
| ② `leftAt === null` | 每次启动都刷新离开时间 |
| ③ 当前不是 `observe` | 仍在观察期就被提前结束 |

⚠️ **M1 是等价变异体（已标注）**：删掉外层 ① 守卫，测试仍绿——因为 `markObserveEpoch` 内部 `if (!Number.isFinite(base.enteredAt)) return;` 同款守卫兜底。**保留外层是为了「不调用就没有副作用」（`save(false)` 也不该跑），不是为正确性。**

## 七、🔴 观察期上限建议

**建议 3~7 天，超过就该切回并补注入。**

理由不是「数据脏」，是**认知偏差会累积**：

- 观察期内每一次她想写，都会以为写成了（因为 prompt 这么说）
- 这些偏差只在切回 `auto` 那一刻一次性补
- **观察期越长，补的那一刻越突兀**

**而且 `observedNotes` 上限 20**——观察到 30 次，补注入只会说「好几次」，但**她累积了 30 次「以为写了」**。

## 十、明确不做的

| 不做 | 理由 |
|---|---|
| 观察期内告诉她「你被观察了」 | 观察者效应，会毁掉观察本身 |
| 把观察条目塞进 `selfNotes` | 会挤掉真实落盘、已铸自传的正式便签 |
| 补注入时给文件名 | 会被理解成「我欠了几个文件没写」 |
| 补注入时给时间范围 | 撞「你不知道现在几点」铁律 |
| 给 `build()` 加「本轮消息」参数 | 要改签名且有多调用点；读 history 尾条是零改动方案 |
| 长期开着 observe 不设上限 | 认知偏差会累积（见第七节） |
