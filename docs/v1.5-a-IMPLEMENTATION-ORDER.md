## 0. 勘察修正（施工前必读）

本施工单在动笔前做了代码核实，**推翻了两个原先的假设**，施工时必须按修正后的方案做。

### 修正 1：错误分类**不需要自己写**，已经存在

`src/openai-transport.js:38-44` 已有完整分类：

```js
function classifyProviderHttpError(status) {
  if (status === 429) return { errorType: 'rate_limited', retryable: true };
  if (status === 500 || 502 || 503 || 504) return { errorType: 'server_error', retryable: true };
  if (status === 401 || 403) return { errorType: 'auth_failed', retryable: false };
  if (status === 400 || 404) return { errorType: 'request_rejected', retryable: false };
  return { errorType: 'http_error', retryable: false };
}
```

且 `makeProviderError()` 会把 `retryable` 写进 `err.retryable`、把状态写进 `err.status`（`openai-transport.js:121,124`）。

**结论**：回落判据直接用 `err.retryable === true`，**不要重新实现一套状态码白名单**——那是第二套判定，迟早与 transport 层漂移（本仓已多次踩过这类坑）。

> 反重力裁决里的「429 + 5xx + 网络故障触发回落，4xx 不回落」，**恰好等于** `retryable === true`。所以裁决本身是对的，但实现方式应该是复用，不是重写。

### 修正 2：`err.retryable` 不能单独用，必须排除 AbortError

`openai-transport.js:234-238` 显式写明：

```js
// Abort/Timeout 保持原语义上抛（non-retryable）；其余网络错误按明确暂态处理
if (netErr && (netErr.name === 'AbortError' || netErr.name === 'TimeoutError')) {
  netErr.retryState = { attempts: attempt + 1, maxRetries };
  throw netErr;    // ← 注意：这里**没有** retryable 字段
}
```

**风险**：用户主动取消（AbortError）时 `err.retryable` 是 `undefined`，不会触发回落（正确）；
但如果将来有人给 AbortError 也加上 `retryable: true`，**用户按了取消却会转去备用端点再发一次请求**——这是真实的事故面。

**必须**在回落判据里**显式排除** `name === 'AbortError'` 与 `signal.aborted`。

## 1. 新增文件：`src/fallback-adapter.js`

### 1.1 接口

```js
function createFallbackAdapter({
  primary,              // 主 adapter（createAdapter 产物）
  secondary,            // 备用 adapter（可为 null = 未配置备用）
  breaker,              // createCircuitBreaker() 产物
  onFallback,           // (info) => void，遥测回调（可选）
  maxFallbacksPerCall = 1,
}) { ... }
```

**必须实现 `createAdapter` 的全部 6 个方法**（`provider-adapter.js:21` 的 REQUIRED_ADAPTER_METHODS）：
`complete / stream / validateConfig / capabilities / normalizeError / usage`。

- `complete()` 与 `stream()`：走回落逻辑（见 §1.3 与 §8.2）；
- `validateConfig / capabilities / normalizeError / usage`：**直接委托给 primary**（无需包装）；
- 若 adapter 上还有 `cfg` / `providerType` 等属性，也要透传。

### 1.2 回落判据（单一真源）

```js
function shouldFallback(err, signal) {
  if (!err) return false;
  // ① 用户主动取消：绝不回落（否则取消按钮等于换端点重发）
  if (err.name === 'AbortError') return false;
  if (signal && signal.aborted) return false;
  // ② 复用 transport 的分类，不自己写状态码白名单
  return err.retryable === true;
}
```

🔴 **断言要求**：这个函数必须能被单独导出测试（`module.exports = { createFallbackAdapter, shouldFallback }`）。

### 1.3 主流程

```js
async complete(msgs, opts) {
  // 未配置备用：退化为纯熔断保护（快速失败，不改变行为）
  if (!secondary) {
    if (!breaker.allowAttempt()) {
      throw makeBreakerOpenError();   // 熔断中如实快速失败
    }
    try { const r = await primary.complete(msgs, opts); breaker.recordSuccess(); return r; }
    catch (e) { breaker.recordFailure(); throw e; }
  }

  // 主端点可尝试
  if (breaker.allowAttempt()) {
    try {
      const r = await primary.complete(msgs, opts);
      breaker.recordSuccess();
      return r;
    } catch (err) {
      breaker.recordFailure();
      if (!shouldFallback(err, opts && opts.signal)) throw err;
      // 落到下面的回落分支
      return await doFallback(err, msgs, opts);
    }
  }
  // 主端点熔断中：直接走备用
  return await doFallback(null, msgs, opts);
}

async function doFallback(cause, msgs, opts) {
  try {
    const r = await secondary.complete(msgs, opts);
    onFallback({ reason: cause ? cause.errorType : 'breaker_open',
                 primaryFailed: !!cause, at: Date.now() });
    return r;
  } catch (fallbackErr) {
    // 两端都失败：如实抛复合错误，不再重试
    const e = new Error('PRIMARY_AND_FALLBACK_FAILED');
    e.code = 'PRIMARY_AND_FALLBACK_FAILED';
    e.primaryError = cause || null;
    e.fallbackError = fallbackErr;
    throw e;
  }
}
```

**硬约束**：`maxFallbacksPerCall = 1` —— `doFallback` 内**绝不递归调用自身**，绝不跨端点循环。

## 8. 已确认的两件事（原「待确认」，现已查实）

### 8.1 `createAdapter` 返回对象有 6 个方法，`stream()` 必须包装

`src/provider-adapter.js:21` 定义：

```js
const REQUIRED_ADAPTER_METHODS = Object.freeze(['complete', 'stream', 'validateConfig', 'capabilities', 'normalizeError', 'usage']);
```

且 `provider-adapter.js:46` 会逐个校验，缺一个就不合法。

**`stream()` 是主对话链路**（`brain.js:1226` `this.api.stream(messages, onDelta, {signal})`）。
**fallback 层必须实现 stream()，否则流式对话完全绕过滤断与回落。**

### 8.2 🔴 流式回落有一个真实陷阱：部分上屏后不能重播

这是本次核实中**最重要的发现**，比「要包装 stream」更要紧。

**事实链**：

1. `main.js:770-771` 的 `onDelta` 直接 `broadcastToWindows('chat-delta', delta)` —— **每个 chunk 立刻推到界面**；
2. `brain.js:1229` 只有在 `stream()` **正常返回**后才拿到 `r.text`；
3. 也就是说：**流进行到一半时，界面已经显示了半句话**。

**如果此时发生 `retryable` 错误并回落**，备用端点会**从头重新生成**，于是：

```text
界面显示：【主端点已吐出】「今天天气真」「今天天气真好呀，我们出去」
                    ↑ 主端点残留          ↑ 备用端点重新吐的
```

**后果**：界面上出现重复、割裂的半句话。这不是「小瑕疵」——它是用户能直接看到的错乱。

**必须的处理规则**（施工强制）：

| 情况 | 处理 |
| :-- | :-- |
| 未吐出任何 chunk（`chunksEmitted === 0`） | **允许回落**，无缝切到 `secondary.stream()` |
| 已吐出至少一个 chunk | **禁止回落**，如实抛错。绝不重播、绝不拼接 |

实现上，fallback 层的 `stream()` 必须**包一层 onDelta 计数**：

```js
async stream(messages, onDelta, opts) {
  let emitted = 0;
  const countingDelta = (d) => { emitted++; onDelta(d); };
  // ... 回落判据里加：if (emitted > 0) throw err;   // 已上屏，绝不回落
}
```

**断言要求**（新增第 10 条）：

```text
10. 流式已吐出 chunk 后发生 retryable 错误 → 不回落、如实抛错、onDelta 不再被调用
    变异：去掉 emitted > 0 判据 → 该断言必 FAIL
```

### 8.3 hot-swap 状态隔离：天然干净

`connection-switch.js` 切换时通过 `createCandidate` 创建**全新 Brain 实例**，
新实例构造函数内新建独立 breaker（状态 `closed`，计数归零）。
热替换失败回滚时，旧 Brain 及其 breaker 状态原样保留。

**无需额外处理**，但要加一条断言确认（第 11 条）：

```text
11. 切换连接后新 Brain 的 breaker 状态为 closed，旧 Brain 的失败计数不影响新实例
```
