## 0. 本文档要解决的问题

v1.5+ 在旧路线图里被描述为「软件工程与开源生态综合阶段」，包含五大支柱。但**经代码实测，五大支柱的状态差异极大**：有的已完成，有的前置条件不满足，有的属于纯 UI 且不改善生命内核。

本文档做两件事：

1. **逐项判定五大支柱的现状**，把不做的那几项**明确归档并写明理由**（不是遗忘，是排期）；
2. **给出 v1.5-a 的技术规格**——唯一一个被判定「有真实缺口、值得现在做」的项目。

### 1.2 支柱一：生命轨迹可视化看板 —— 归档至 v1.6+

**实测**：`index.html`（22,807 字节）中只有一处相关文本：`状态轨迹 (JSON)` 按钮，那是研究者面板导出 JSON 用的，**不是可视化看板**。三套视图（沃丁顿流道图 / 记忆星云 / 编年史）**一个都没有**。

**归档理由（不是不做，是现在做性价比低）**：

1. **它是纯观测工具，不改善任何智能行为**。看板做出来，初澜的行为一个字都不会变——它服务于「人看数据」，而当前阶段的核心诉求是「她更像活着」。
2. **工程量大而验证价值低**。三套视图需要引入图表库、设计拓扑布局、处理大量渲染逻辑，工作量超过 v1.3 + v1.4 之和，但唯一收益是「更容易观察已有数据」。
3. **前置条件未成熟**。沃丁顿流道图需要「从幼态到成熟」的长期轨迹才有意义，而当前 `subject-state.json` 只有 5 个窗口的历史——画出来是一条接近直线的短轨迹，**看不出任何东西**。
4. **数据源已就绪，随时可做**。`canalization.js`、`memory-dynamics.js`、`experiences-archive.js` 的数据都是现成的，将来任何时候都能接，**不存在技术债累积**。

**重新激活条件**：窗口数 >= 50，且用户明确提出「想看她这段时间是怎么变的」。

### 1.3 支柱二：布隆过滤与轻量检索 —— 归档至数据量达标后

**实测**：`git grep bloom -- src/` **零命中**，未实现。当前 `experiences.jsonl` 只有 **10 条记录 / 566 KB**，`D-23` 召回走全量扫描。

**归档理由**：

1. **问题尚不存在**。路线图自己写的前提是「长期相处数月乃至一年后积累海量事实」。当前 10 条记录下，全量扫描成本**可以忽略**。
2. **布隆过滤器有假阳性**。它是概率数据结构——「可能包含」不等于「一定包含」。为一个不存在的问题引入一类新的误差来源，是净负收益。
3. **过早优化会固化错误的索引结构**。等到真需要时，对「该索引什么」的理解会比现在准确得多。

**重新激活条件**：`experiences.jsonl` 记录数 >= 5000 条，且实测召回耗时 > 50ms。

---

### 1.4 支柱五：主观时间感知（重逢心境）—— 归档至 v1.6+

**实测**：`git grep 重逢 -- src/` **零命中**。但 v1.3-b 已实现 `idleness_deep`（45 分钟）与 `idleness_verydeep`（90 分钟）两档静默感知。

**归档理由**：

1. **与 v1.3 的沉默机制存在重叠风险**。再做「重逢心境」很容易变成「第三档、第四档静默阈值」，导致阈值越堆越多、彼此冲突，**最终没人说得清她到底该在什么时候说什么**。
2. **要做就必须先重构现有阈值体系，而不是叠加**。那是一次有风险的改动，值得单独一个版本，不该塞在 v1.5 里顺手做。
3. **「沉默留白」这一半已交付**（v1.3-b），生命体验的缺口不像想象中那么大。

**重新激活条件**：明确「重逢」与「静默」的语义边界（前者关注「离开多久后回来」，后者关注「离开期间她做什么」），且愿意为此重构阈值体系。

## 2. v1.5-a：Provider 容灾自动回落

### 2.1 为什么这是唯一值得现在做的

**实测发现的真实缺口**（`src/circuit-breaker.js:4-5` 的文件头自己写着）：

```text
【Staged 预留阶段】本模块已实现并有回归覆盖，但暂未接进主干生产编排
（brain.js 主链路当前无真实熔断流量经此流转）——INT-01：实现 ≠ 运行时。
```

`git grep createCircuitBreaker -- src/` **只有定义处，零调用点**。

也就是说：

- **熔断器写好了，但没人用**；
- **主端点挂了不会自动切备用**，用户只能看到报错或手动去设置里切；
- `connection-switch.js` 只支持**手动切换**（用户点选），不是自动回落。

这是一个**真实存在的健壮性缺口**，而且不触碰生命内核（纯基础设施），风险可控。

### 2.2 设计原则（三条硬边界）

1. **绝不改写作息/记忆/身份**：回落只换 adapter，不动 `SubjectState` / `memory` / `selfLedger` / `birthAt`。与 `connection-switch.js:15-17` 的 Subject Isolation 铁律一致。
2. **breaker 状态永不进入 provenance**：沿用 `circuit-breaker.js:12-13` 的红线——「熔断只控制是否允许尝试，不参与 provenance 真值判定」。
3. **回落必须可观测**：每次回落写遥测（`fallback_used`），否则用户永远不知道自己在用备用端点。

### 2.3 架构方案（待评审）

**核心问题**：`brain.js:212` 是单点 `this.api = createAdapter(...)`，要支持回落有两个可选路径。

**路径 A（推荐）：Adapter 层包装**

```text
createFallbackAdapter({ primary, secondary, breaker })
  complete(msgs, opts) 内：
    if (breaker.allowAttempt()) {
      try { r = await primary.complete(...); breaker.recordSuccess(); return r; }
      catch (e) { breaker.recordFailure();
                  if (shouldFallback(e)) return secondary.complete(...); throw e; }
    } else {
      return secondary.complete(...);   // 主端点熔断中，直接用备用
    }
```

**优点**：`brain.js` 只需改一行，所有上层逻辑零改动。

**路径 B：Brain 层重试**——在 `this.api.complete` 调用点包 try/catch。

**缺点**：`brain.js` 有 4 处 `api.complete` 调用（:1359 / :1941 / :2390 / :2620），每处都要改，容易漏。

**建议走路径 A。**

### 2.4 必须回答的开放问题（施工前需拍板）

1. **备用端点从哪来？** 用户在设置里配第二条连接，还是硬编码一个公共备用？
2. **哪些错误该触发回落？** 网络超时/5xx 该回落；**4xx（401 鉴权失败、400 参数错）不该回落**——那是配置问题，换端点也没用。
3. **回落是否要告知用户？** 界面提示「正在使用备用连接」，还是静默？
4. **回落是否有次数上限？** 防止两个端点都挂时来回重试烧钱。

### 2.5 验收判据

```text
① 主端点正常时，备用端点零调用（用 mock 计数验证）
② 主端点连续失败 3 次后，第 4 次直接走备用（不浪费一次失败）
③ 主端点恢复后（cooldown 到期探测成功）自动切回
④ 4xx 错误不触发回落（构造 401 验证）
⑤ breaker 状态不出现在任何 provenance / 归档记录里（静态扫描断言）
⑥ 回落事件写入遥测，可查
⑦ 两个端点都失败时，如实报错，不无限重试
```
