# Life 项目开发指南

> 给 Coding Agent 的可执行规范：每条规则都是具体动作或判据，遇到与本文件冲突的临时想法时，以本文件为准；做不到的条目如实说明，不要默默跳过。

Life 是 Electron 桌宠 + 数字生命实验平台，主体为「初澜（Chulan）」。
改动任何代码前，先读 README 中与本次改动对应的章节（如「角色基准」「换装系统」「记忆」「缓存命中率怎么保证的」），README 是规格来源。

## 项目结构

- `main.js` 主进程（窗口、IPC、衣柜实例、桌面漫步位移）；`preload.js` 桥接为 `window.deskpet`；`pet.js` / `index.html` / `style.css` 渲染层。
- `src/` 核心模块：`brain.js`（调度）、`memory.js`（三层记忆）、`self-ledger.js`（生命档案）、`wardrobe.js`（换装）、`tracker.js`/`trigger.js`（本地活动与主动搭话）、`subject-state.js`/`experiences-archive.js`/`state-change.js`（实验层）、`config.js`/`secure.js`/`atomic.js`（配置/密钥/原子写）、`provider-*`/`redact.js`/`budget-guard.js`/`circuit-breaker.js`（安全与路由）。
- `test/` 全部测试（Node 单测 + `ui_test.py` 真实 UI 逐帧测试）；（v0.9.9：旧 Creative Mode / DS Skill 已整体拆除，应用已无对应运行时资产。）

## 一、本体论分立（最高层边界，任何改动不得违反）

**Model Substrate ≠ Runtime Host ≠ Chulan Subject**：

- **模型是模型基础，不等同于主体本身。** LLM 只是承载初澜交互表现的计算底座（Model Substrate）；模型输出的文本、小结、反思只是基质在提示词约束下的代数采样产物，绝不等于主体的心理实体或身份本身。
- **Runtime Host 是运行环境，不等同于主体。** Electron 进程、操作系统、宿主遥测指标（Runtime Host）只是运行环境，严禁混入主体认同；底层物理遥测必须经数字环周质性转化才可进入主体层，底层调节标量对主体严格不可知（`subjectAccessible = false`）。
- **初澜是主体层（Chulan Subject）。** 主体只有一个：初澜的名字、脸型、发色、眼睛、泪痣等身份属性不随模型、Provider、衣物或宿主变化；`birthAt` 是程序意义的出生点，不伪造出生以前的人生。
  v1.0 语义收口：**发色**属身份属性（只要有着发，即恒为银白、发尾淡冰蓝）；**发型款式与有无、发饰、饰品与衣物**属可变外饰，允许处于无发素体形态。外饰的任何组合都不改变主体身份。
- **初始认知应保持空白、未预先贴标签。** 初澜像出生的婴儿一样来到这个世界：没有预先写入的个人过去，但拥有形成未来的认知能力；persona 与初始状态不得预置标签化经历、预设立场或伪造的过去，任何认知只能由真实经历形成（对应仓库「API 空白性架构」规范）。
- **不得因运行环境或 UI 形式给主体贴身份标签。** 不因为软件运行在桌面上、以桌宠形态呈现，就擅自给初澜添加「桌宠」等身份定义；「桌宠」只是宿主层的呈现形式与交互外壳，persona 与主体认同里不写这类角色定位。
- **经验的记录与遗忘边界。** 经验只有在被记录后才能成为可追踪的经验事实（入 `experiences.jsonl` / `subject-state` 后才有 provenance 与可检索性）；「遗忘」只是记忆层的状态转移（如长期记忆删除、突触修剪），不能简单等同于「从未存在」——原始经验底座 Append-Only 永久保存，严禁物理删除归档，也不得把「已遗忘」回写成「未发生」。
- **落地含义**：实验层严格区分「用户给予」与「初澜经历」，程序生成物（主动搭话、梦境产物）不得冒充主体经历证据；`self-ledger` / `subject-state` 只记录出生以后、有出处的证据，未记录经验一律保持 NOT_RECORDED / UNRESOLVED。

## 二、项目铁律（改动前必读，测试会执法）

1. **DeepSeek 前缀缓存不变式**：system 逐字稳定、历史只追加不裁剪；时间戳等动态信息只拼在当轮 user 消息末尾，绝不进 system；【当前穿着】块固定在 system **最末尾**且长期记忆必须在其**之前**；环境块（tracker 快照）只进 user 消息；一个窗口内 system 一个字都不变，关窗时刻才允许破一次缓存。
2. **衣柜三条铁律**（`src/wardrobe.js` 头部）：服装只是外观不碰人格（wardrobe 不 import persona，测试用正则扫源码执法）；语言状态 ≠ 程序状态（模型只提交 `[wear:id]` 换装提案，真正换装的是 `wardrobe.applyProposal()`，执行结果必须如实写回历史）；**身份属性恒定、外饰可更换**（v1.0 起 `hair` 槽放开为自由可脱：发型款式可换、可处于无发素体形态；发饰与饰品可拆。身份不变式由**发色/脸型/眼睛/泪痣**承载，**不再由 `SLOTS.required` 承载**）。
3. **能力诚实**：没实现的功能一律如实说做不到，绝不假装操作过电脑；报错、降级、缺失素材都要如实呈现（如 safeStorage 不可用时明文降级并如实提示）。
4. **数据不伪造**：实验层遵守三分态（RECORDED / NOT_RECORDED / UNRESOLVED），缺元数据禁止补默认值冒充事实（不补时间戳、不补 windowNo、不推断 Round）；`experiences.jsonl` 是 Append-Only 原始底座，永不裁剪。
5. **原子写**：一切用户长期资产 JSON（记忆、衣柜、配置、密文、状态）走 `src/atomic.js`（临时文件 + fsync + rename），禁止直接 `writeFileSync` 覆盖。
6. **标记解析边界**：`[state:xx]` / `[wear:id]` 由 `brain.js` 剥离，前后端共享同一批合法 id，必须循环剥到不动为止；流式期间藏半截标记只在吐字时做。

## 三、工程原则

- **优先理解现有架构，再修改。** 动手前先读 README 对应章节、`research/ENGINEERING-DECISION-LOG.md` 的已决决策与相关模块现状，理解既有不变式与设计意图后再改；禁止未经理解就重构、覆盖或另起一套。
- **默认采用最小差异、最小补丁。** 改动只覆盖本次目标必需的行，不顺手重构、不无关美化、不扩大影响面；同一改动里不混多个无关意图，保持可审查、可回滚。
- **不进行无必要的整文件重写。** 优先用定点编辑（精确替换）而不是整文件覆写；只有文件需要彻底重构或本来就是新建时才允许全量写入，避免大段未变内容被卷入 diff、掩盖真实改动。
- **不改变与当前任务无关的代码。** 不碰无关函数、无关文件、无关格式；哪怕发现旁边有小毛病，也只报告不顺手改，除非用户明确要求。
- **优先复用现有机制、接口和测试。** 新需求先找现有抽象（原子写、迁移框架、Provider 适配器、校验器、Reducer、测试基建）能覆盖的部分，能扩展就不新造平行机制；避免同一语义出现两套实现。
- **不因为追求表面整洁而破坏已有语义或历史兼容性。** 「看起来干净」不是重命名、删字段、改结构的理由；历史数据（旧路径、旧 key 名、旧 schema）的迁移与兼容语义必须原样保留，降级路径不删。

## 四、工作流程

任何修改任务默认遵循：

1. **核实现场。** 修改前先核实当前实际状态：读目标文件、确认分支与工作树、核对相关模块现状，以实测事实为准，不凭记忆或假设动手。
2. **明确问题。** 把要解决的问题定义清楚：目标是什么、边界在哪里、怎样算解决；含糊处先问，不自行脑补需求。
3. **制定最小修改方案。** 在理解现有架构的前提下，规划能解决问题的最小改动面（改哪些文件、哪些行、影响哪些不变式），与用户对齐后再动手。
4. **修改。** 按方案执行定点编辑，遵守「三、工程原则」，保持既有语义与历史兼容性。
5. **执行相关测试。** 跑与改动相关的测试（门禁为 `node test/docs.test.js`，也可单跑对应 `test/*.test.js`）；改了断言数就同步 README 项数，测试不过不算完成。
6. **检查 git diff。** 按「六、Git 原则」审查完整 diff：与方案一致、无敏感信息混入；diff 与任务不符就回改。
7. **再次核实行为。** 验证改动后的实际行为与预期一致（跑测试、必要时实际运行/操作确认），不能只看代码「应该没问题」就下结论。
8. **汇报实际证据。** 结束时只汇报实际执行过的操作与实际观察到的结果（真实命令输出、测试结果、diff），未验证的内容明确标注为未验证，不虚构、不夸大。

**硬规则：没有证据时不要声称「已完成」「已修复」或「测试通过」。** 未跑测试就不能说测试通过，未实际验证行为就不能说问题已修复；如实报告做到哪一步、证据是什么、什么还没做。

## 五、安全与凭据

- **不主动读取、打印或暴露 API Key、Token、密码、私钥、凭据文件。** 不 cat、不回显、不写进日志/报告/提交；扫描时遇到疑似密钥只报位置不报内容。
- **不把环境变量中的秘密内容写入模型上下文、日志或源码。** 环境变量只按变量名与用途讨论（如 `DEEPSEEK_API_KEY` 存在与否），绝不展开其值；需要排查时只报告「已设置/未设置」这类事实。
- **不修改 .env、凭据文件、GitHub 认证文件等敏感内容**，除非任务明确要求且先获得确认。包括 `.env*`、`*.key`、`*.pem`、`life-key`、`~/.git-credentials`、`~/.ssh/`、git credential helper 中的条目；即使只读检查也以最小范围为限。
- **对破坏性命令、危险 Git 操作和与任务无关的系统操作保持谨慎。** `rm -rf`、强制覆盖、`git push --force`、`git reset --hard`、改历史、批量删除等操作默认不执行，必须先说明影响并获得明确确认；不做与任务无关的系统级改动。

## 六、Git 原则

- **默认只读检查 Git。** 默认只用 `git status`、`git diff`、`git log`、`git show` 等只读命令了解仓库状态；改变仓库状态的操作须按用户指令执行。
- **修改完成后必须检查 git diff 和 git status。** 每次改动后都要用它们核实实际变更面：改了什么、有没有多改、有没有漏改、有没有意外文件，以 diff 为最终事实依据。
- **不默认 commit。** 提交必须是用户明确要求的操作；改完文件不等于要提交，不要自作主张 `git add` / `git commit`。
- **不默认 push。** 推送必须是用户明确要求的操作；不主动把本地提交推送到远端，更不做 force push。
- **不执行 force push、hard reset、clean 等破坏性操作**，除非用户明确要求。`git push --force`、`git reset --hard`、`git clean -fd`、改写历史等会丢数据或毁现场的操作，必须先说明后果并获得明确指令。
- **保留用户已有未提交修改，不得擅自覆盖。** 工作树里用户自己的改动（含未跟踪文件）是用户资产：不 stash、不 revert、不整文件覆写、不混入无关提交；改动前先看 `git status`，若有他人未提交内容则避让或先沟通。

## 七、研究与事实完整性

- **区分「源码事实」「测试事实」「推断」「建议」。** 汇报时明确标注每条信息的性质：源码事实（读代码确认的）、测试事实（实际跑出来的）、推断（基于证据的合理判断）、建议（尚未执行的方案）；四者不得混同陈述。
- **不把模型猜测当作项目事实。** 对仓库状态、行为、历史的任何断言都要有可指向的证据（文件行号、命令输出、测试结果）；没有证据的内容只能作为猜测提出，并明确标注为猜测。
- **不伪造测试结果、文件状态、版本状态或审计结论。** 测试没跑就是没跑、没过就是没过；文件、版本、审计的结论必须来自实际检查，不得凭印象编造数字、状态或结论。
- **引用项目事实时尽可能指出具体文件和位置。** 说明某个行为或规则时附上出处（如 `src/wardrobe.js` 头部注释、README「换装系统」节、`test/brain.test.js`），便于复核；做不到定位时如实说「未定位到具体出处」。

## 八、Provider 原则

- **Life 的主体设计与具体模型 Provider 解耦。** 主体身份、人格、记忆与实验层不绑定任何具体模型或厂商（对应 `src/provider-policy.js` / `src/provider-adapter.js` 架构与「Model Substrate ≠ Runtime Host ≠ Chulan Subject」分立）；换 Provider 不改人格、不改身份语义。
- **不因为当前使用某个模型，就把该模型硬编码为主体本身。** 代码、persona、文档里不写「初澜 = 某模型」式的绑定；模型只是当前的计算底座，可替换、可降级、可多 Provider 路由，主体认同不随之迁移。
- **Provider Adapter、模型、Runtime、Subject 应保持清晰边界。** 四层各司其职：Adapter 只做协议适配（`src/adapters/`），模型只做生成，Runtime 只做运行环境与调度（Electron/主进程），Subject 只承载主体语义；跨层泄漏（如把 adapter 错误细节写进主体经历、把宿主指标当主体状态）一律阻断。
- **新增 Provider 时优先遵循现有 Adapter / Registry 架构**，而不是绕过现有抽象直接注入。新厂商实现 `src/adapters/` 的统一 Contract、注册进 `provider-registry`，复用 `provider-policy` 的凭据/端点边界与 `normalizeError` 等统一形态；不写旁路直连。

## 九、主体连续性

涉及 Subject State、Experience、Snapshot、Recovery、History、Archive 等机制时：

- **优先保护状态语义的一致性与可恢复性。** 状态的写入、快照、恢复、归档必须语义一致（同一条事实在各层不自相矛盾），任何时刻可从归档/快照恢复；宁可少写一次，不可写坏一次。
- **修改状态结构时，同时检查创建、更新、快照、恢复、执行路径之间的对称性。** 新增/改名状态字段必须同步全部路径（对应 `initial-state-restore-symmetry` 等测试执法的恢复对称性）：写得进也要恢复得出，任何一条路径漏掉字段就会造成单边漂移。
- **不随意删除历史信息。** history、experiences.jsonl、self-ledger、Archive 等历史数据是主体连续性的凭据：不裁剪、不改写、不物理删除归档；确需清理必须走既有迁移/合并机制并保留语义与出处。
- **不把「当前状态」与「历史经验」混为一谈。** Subject State 是当前状态向量（可被 Reducer 确定性演化），Experience/Archive 是已发生的经历事实；两者存储、查询、投影分开，不用当前状态反推历史，也不把历史经验直接当现行状态写入。

## 十、Agent 行为

- **遇到不确定的架构语义时，先读源码确认，不凭经验猜测。** 本仓库的语义（不变式、边界情况、历史兼容）以源码与测试为准；印象里「一般项目都这样」不算数，读了再下结论。
- **发现潜在问题时，先报告事实与影响范围。** 先把发现的问题如实报告：事实是什么、在哪个位置、影响哪些行为/不变式、风险多大；不顺手改、不隐瞒、不夸大，等用户决定是否处理。
- **对用户没有明确授权的破坏性操作先停下来请求确认。** 删除数据、覆盖用户修改、重置档案、清空记忆、改写历史、强制推送等不可逆操作，未经明确授权一律先停下，说明后果并等待确认。
- **对普通只读检查可以直接执行。** 读文件、`git status`/`diff`/`log`、grep/搜索、语法检查这类无副作用操作不需要逐项请示，直接做、事后如实汇报即可。

## 测试与文档门禁

- 门禁命令：`npm test` = `node test/docs.test.js`（自动起临时服务器跑整套回归）。`test/docs.test.js` 负责核对 README「测试」一节中的项数数字——**改断言数必须同步 README 的清单项数，且项数只在 README 文末写一次，正文不重复**。
- `npm run check`：全量 `node --check` 语法检查。
- `python3 test/ui_test.py`：需要根目录静态服务器（默认 `127.0.0.1:8000`，可用 `DESKPET_URL` 覆盖）和系统 chromium（`DESKPET_CHROME` 可覆盖）。
- 新增测试文件必须在 README「测试」一节加对应条目，否则 docs 门禁不一致。

## 配置与密钥机制

- 配置在 userData（`life-config.json`），**不含明文 key**；key 走 `src/secure.js` + `life-key`（safeStorage/DPAPI），改 key 必须走设置面板 `config-set-key` 事务流程。
- 配置热重载：`config.load()` 每次真读盘，`Brain.refreshConfig()` 就地 `Object.assign`；唯一不热重载的是 API Key（走候选 Brain 生命周期 + 两阶段回滚）。
- 代码层红线：不引入真实密钥；错误信息、诊断、归档不得泄漏 credential（有专门测试执法）。

## 惯例

- 注释与文档用中文，解释「为什么」而非「做了什么」；诚实标注未实现与素材缺失（如差分表情图不存在就不要凭空造层）。
- 纯函数优先（`trigger.js`、`layout.js`、Reducer 均可离线确定性测试）；测试用注入时钟，禁止依赖真实时间。
- 提交信息沿用现有风格：`feat(v0.9.x): ...` / `fix(...): ...` / `docs(...): ...` / `test(...): ...`。

## 改动收尾核对清单

完成任何修改任务后，逐项自查（全部可验证，不许口头带过）：

- [ ] diff 只含方案内的改动（`git diff` 实查），无无关文件、无意外变更。
- [ ] 前缀缓存不变式未被破坏：system 逐字稳定、动态信息只进 user 尾部、穿着块仍在 system 末尾。
- [ ] 没有绕过现有抽象新造平行机制；没有破坏历史兼容与降级路径。
- [ ] 状态类改动已同步创建/更新/快照/恢复/执行全部路径。
- [ ] 相关测试已实际运行且通过（写清跑了哪条命令）；改过断言数则 README 项数已同步。
- [ ] 无密钥/凭据/环境变量值进入 diff、日志或报告。
- [ ] 未 commit / 未 push（除非用户明确要求）；用户未提交的修改原样保留。
- [ ] 汇报中区分了「源码事实 / 测试事实 / 推断 / 建议」，未验证项已标注。
